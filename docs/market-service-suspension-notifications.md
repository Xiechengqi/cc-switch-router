# 服务暂停通知与历史积压恢复

## 状态与资金规则

付费 Client／Share（含试用）下单前必须具备首个计费周期所需的可用余额；
试用期间不扣款、不冻结余额。月付、按量试用共用转付费检查路径，只有
资金优先级、财务隔离、余额、扣账和周期建立均成功后才能转为付费。

试用耗尽且首次扣款失败时，合约在同轮对账中从暂时的 `suspended` 转为
`ending`，立即派发 Client 清理或 Share 撤权，不进入已付费服务的 7 天保留期。
后续补款不能复活旧试用，需要重新下单。此前已暂停、从未开始付费且试用
耗尽的历史租用也适用；财务冻结仍优先阻止不安全的资金及服务处理。

已有付费服务续费／预算不足时，仍按原有暂停窗口处理（默认第 5 天提醒、
第 7 天回收）。后台重试不能反复刷新暂停起点、制造重复通知。

同一次持续暂停以 `contractId + suspended_at` 标识，不使用同时承担后台轮询
游标职责的 `updated_at`。真实恢复后再次暂停可以生成新通知。发送前必须
同时匹配用户、当前状态和暂停起点，旧暂停／终止提醒不因再次暂停而复活。

渠道任务沿用历史幂等键和冻结信封。过时通知停止后续投递；已发送回执不改写，
在途任务的有效租约不被另一 worker 抢占，过期但接受情况未知的任务保留
`uncertain`，不能假装从未发送。

## 迁移 89

迁移在正常启动、业务 worker 启动之前事务执行，不需要手动删除通知或资金记录。

仅当证据明确证明是同一次“从未转付费的试用结束”时，恢复原暂停起点：

- 当前暂停且不属于财务冻结；有激活时间、试用已耗尽，从未开始付费。
- 没有已付周期、预算或资金冻结记录，没有真实恢复／终止事件。
- 存在多条身份、原因、事件键和时间都一致的余额不足暂停通知。
- 原暂停时间不早于独立保存的健康试用结束证据。

符合条件的服务恢复首条暂停通知的时间；如果资金优先级游标被重试推迟，
恢复到独立试用证据的结束时间。财务冻结、已付费、真实恢复、证据不明或
格式异常的合约不回溯修改暂停起点。

过时的排队暂停／终止提醒及重复投递任务被终止。已通知或接受情况不明的
持续暂停不再补发；完全未投递的持续暂停最多保留原始一条待发通知。
已发送回执、原始事件载荷、邮件信封、幂等键、尝试次数和未知接受结果保留。
充值、转账、C2C、账本、资金冻结、计费周期和试用证据不改写。

迁移不增加业务表；仅增加通知对象索引。真实 schema 回归仍检查当前表数量，
新增用例位于 `schema::tests::suspension`，纳入现有迁移 CI。

## 验证与部署边界

回归覆盖首期余额校验、试用不冻结资金、首次扣款失败同轮回收、后续补款
不复活旧试用、历史暂停试用回收、付费服务暂停空档不收费、真实二次暂停、
过时通知、独立渠道租约、已发送／未知回执保留，以及付费服务的第 5 天提醒、
第 7 天终止。

远程验证只能在只读数据库的内存副本上演练迁移，不运行真实发送、充值或
服务控制。部署新二进制后才会修复线上 worker，并在启动时处理历史积压；
单独清队列或重启旧二进制仍会重新产生通知。

上线前备份数据库及其必要密钥。迁移后旧版本不能直接读取更高 schema，
不能仅回滚可执行文件；需要遵循带备份的正常版本升级／回退流程。

## 迁移 91：独立防风暴与最终投递

事件幂等不能防止异常状态机不断生成不同事件键。渠道首次发送前，在同一个
Immediate 事务内检查并占用独立预算；重启、并发 worker 和事件键变化不能
绕过预算。重试仍使用原任务、冻结信封和幂等键，不重复占用首次尝试额度。

默认规则（可在“设置 → 通知 → Email (Resend)”修改，保存后重启）：

- 同一次持续暂停仍只通知一次。真实二次暂停允许新事件，但同服务暂停提醒
  冷却 30 分钟，滚动 24 小时每用户／渠道最多 3 封。
- 同用户、渠道跨服务每小时最多 10 条服务提醒。市场服务邮件全平台滚动
  24 小时最多 50 封；默认预算为登录和资金回执留出余量，不是 Resend 额度保证。
- 暂停、恢复、终止提醒、缺款提醒及其摘要共享服务预算。充值、转账、C2C
  成交回执和安全通知不套用此策略；队列优先领取资金通知。
- 服务提醒过期 1 小时不再新提交。已尝试但接受结果不明的过期任务记为
  `uncertain`，不冒充从未发送；已接受的历史任务永不重排。
- 被限制的业务和站内事件不删除。每用户合并一个延后状态摘要，发送时读取
  涉及服务的当前状态，仍受预算限制；不会逐封补发被抑制的中间状态。
- 首次触及限制通过原有 Operator Telegram/Bark 链路告警，同原因每小时
  最多一次，不额外发送用户邮件。

迁移 91 只增加通知元数据和归一化跟踪表，不修改账本、合约、邮件信封、
幂等键、尝试次数或已有发送状态。历史 `sent` 仅回填为网关 `accepted`，
不假定已送达，也不触发重发。迁移 90 的密码登录表及历史会话不受影响。

### 投递跟踪

`market_notification_deliveries.status='sent'` 继续代表渠道接受；邮件的
`provider_status` 独立表示 `accepted / delayed / delivered / failed /
bounced / complained / suppressed`。`delivered` 仅表示收件服务器接受，
不表示用户已阅读。晚到、重复、乱序回调只能更新归一化事实，不能产生业务
事件或发送请求；sent/delayed 不会将 delivered 降级。

可选配置 Resend Webhook：

1. Resend 控制台创建 `https://<router-domain>/v1/webhooks/resend`。
2. 订阅 `email.sent`、`email.delivered`、`email.delivery_delayed`、
   `email.failed`、`email.bounced`、`email.complained`、`email.suppressed`。
3. 将 Resend 生成的 `whsec_…` 保存到设置中的 Resend 投递回调密钥并重启。
   密钥不公开，不是 DujiaoPay Webhook Secret。

验签使用原始请求体、Svix ID／时间戳／HMAC，时间容差 5 分钟，正文上限
64 KiB；按事件 ID 去重。回调早于发送响应时，暂存有界、无原始正文的
归一化证据，在接收回执落库时绑定。未知邮件最多暂存 1000 条、保留一天；
已绑定投递事件保留 30 天，不删除原始业务／提交回执。

独立跟踪 worker 每分钟最多读取 5 封邮件状态，请求之间至少 750 ms；
查询不会阻塞发送 worker。未配置回调仍可用查询补偿，但 API Key 必须有
读取邮件权限。401／403 暂停查询 6 小时，429 尊重有界 Retry-After；
网络错误也触发全局退避。只跟踪近 7 天未终结邮件，凭据变化不会拿新
账户的 key 查询旧账户邮件。查询失败不等于邮件失败，也不触发重发。

### 管理员诊断与验收

“运维 → 通知中心 → 市场邮件投递”显示提交／最终投递两层状态、延迟和
失败数量、暂停事件／提交最新时间、待处理数、策略预算、抑制原因及关联 ID。
只读接口为 `GET /v1/admin/market-notifications`，支持 `cursor`、`status`、
`purpose`、`recipient`（用户 ID），每页 50 条；必须管理员会话，不返回
原始信封、密钥、完整邮箱或回调正文。

本地回归必须覆盖不同事件键风暴、冷却／每日上限、收件人／渠道隔离、
资金回执优先级、旧提醒过期、未知接受结果、签名／重放／乱序回调、
回调早于发送响应、查询权限／退避／租约，以及真实迁移和新库重复打开。
不发送真实邮件、不修改远程数据、不做 UI 截图。

前端 `npm --prefix frontend run test:market-notifications` 验证两层状态映射；
构建导出后运行 `npm --prefix frontend run test:market-notifications-browser`，
使用本地模拟接口验证汇总、筛选、游标翻页、错误恢复、中英文及管理员可见性。
浏览器测试不截图、不连接真实邮件服务，不提供重发操作；两组检查均纳入 CI。

上线后观察持续余额不足服务至少一个冷却窗口，并核对一天内的预算。
没有新暂停事件／API 提交但仍收到邮件时，用原始 Message-ID／Received
邮件头匹配历史 provider_message_id；删除本地记录或重启不能撤回旧邮件。

# 账户市场与快捷余额交互契约

本次改造基于历史会话 `2026-10-29-041450-local-command-caveatthe-command-below-was-run-d.txt` 中批准的账户交互方案。保留现有 Client Market 的五条一页租用审计、页码跳转与导航修复；不改变资金账本、试用规则、退租补偿或服务收费。

## 页面分工

| 入口 | 负责内容 |
| --- | --- |
| 账户 → 市场交易 → Share 市场 | 我租用的服务及历史；我出售的 Share、车位和租户 |
| 账户 → 市场交易 → Client 市场 | 我租用／出售的 Client、历史租约及对应退租结算 |
| 账户 → 市场交易 → 供应商中心 | 收入、买家准入、业务联系信息三个标签 |
| 账户 → 资金 → 平台余额 | 充值、C2C 买卖及订单处理、余额转出、充值记录与流水 |
| 顶部导航栏余额 | 当前页面内快捷充值、C2C 购入、余额转出；链接到完整钱包 |

## 账户市场表格

- 四个交易视图共用 `ExpandableRecordTable`。主行只显示名称、对方、状态、价格及适用的期限；手机端隐藏的次要字段在展开区仍可查看。链接和按钮不触发行切换。
- 展开状态按不可变记录 ID 保存，轮询更新不清空；只有展开后才挂载续费、服务争议等详情组件，避免每一行独立请求。
- 需要关注的记录优先，其次是当前服务按到期时间排列，已结束记录最后、较新记录在前。缺失或非法日期不影响稳定排序。
- `?tab=user|provider&focus=<record-id>` 可打开对应行。Share 租用使用 subscription ID，Share 出售使用 listing ID，Client 使用 installation ID；历史焦点不在第一页时依次加载后续游标，重复游标终止遍历。
- Share 历史保留加载更多，Share 市场自身历史仍保持每页五条及翻页；Client 退租记录独立按角色分页，初始加载和轮询只读当前角色，不逐行查单。已清理或不在当前租约响应里的退租单作为历史行保留，不凭时间过滤掉。
- Client 退租详情、答复、减免、撤回等使用同一个页面级 `ClientTerminationDialog`；刷新不会销毁弹窗。市场行内红色处理入口及 Router owner 裁决权限保持不变。
- 当前 Host 再次出租不会让旧租约显示新租户的身份或 Client 链接。未记录的历史主机名不猜测，用原 installation ID 显示。
- Client 轮询比较器覆盖 Host／租约类型的全部字段；新增可选字段也必须先指定比较策略才能通过类型检查。试用剩余、续费策略、到期、争议和下一轮试用额度独立于 `updatedAt` 更新，不复用过期状态；等价响应仍复用已有对象。

## 供应商中心

- 路径仍为 `/account/provider-settings/`，标签使用 `?tab=income|access|contact`；明确的 query 优先，原 `#income` 锚点映射到收入。
- 没有指定标签时，以后端 `hasFinanceActivity` 判断：有记录显示收入，否则买家准入。判断失败给出说明并降级到准入，仍可手动打开收入。
- 准入标签显示待办数量，待处理申请排在最上面；批准／拒绝完成后即时更新数量，并保留定期同步。
- 收入页只管收益、服务费、冻结及自动到账。退租流程不再放在收入或钱包页；没有恢复独立收益旧路由、提现或手动收益入余额。

## 充值方式与迁移 100

- `GET /v1/market-wallet/channels` 新增 `methodCategory: "crypto"`。买家根据这个后端分类选择「加密货币」，不展示商户名，也不从商户名称／`gatewayKind` 推断方式；未知或缺失分类不开放支付。
- 无论有一个还是多个选项，都使用现有 styled select；direct 模式的具体链、币种选择不变。
- 当前仅有 DujiaoPay 适配器。启用 API 与数据库触发器共同阻止同一 gateway kind 新增第二个 active 渠道，canary 同样计入。冲突返回 HTTP 409、`MARKET_PAYMENT_METHOD_CHANNEL_ACTIVE` 及冲突渠道的安全展示信息。
- 替换商户须先停用旧渠道，再启用新渠道；轮换同一渠道密钥、编辑展示资料及 canary→live 不受影响。原订单仍绑定原渠道／修订继续对账，不改绑商户。
- 采用增量触发器而不是直接创建唯一索引：已有多 active 的部署仍能升级启动，不自动停用真实收款或改写历史订单；只禁止新增激活。用户端同类方式按 Owner 排序只显示第一条。Owner 应停用多余渠道；停用后不能在另一条仍 active 时重新启用。
- 本迁移不增加金融表，不删除或重记订单、回执、流水，不改写已发布迁移。未来新增另一家 crypto 适配器时，必须将约束从 gateway kind 扩展为跨适配器的 method category，不能只改前端映射。

## 快捷余额与支付安全

- 导航栏余额改为按钮，对话框首次点击才懒加载。仍在钱包页时，只滚动并聚焦已有操作区，不同时创建两份表单。
- `WalletTopupForm` 是完整钱包和快捷弹窗的唯一充值实现：本金 1–1,000 美元，维护费采用 Owner 动态费率，报价版本、过期重报、幂等键与新付款标签页共用。
- 切换操作保留充值草稿及不确定建单的原幂等键，非充值标签暂停报价／渠道轮询；创建请求完成前禁止关闭／切换。关闭后重新打开，先读取权威钱包和充值记录，读取失败不能提交充值。
- 付款标签页在用户点击时同步创建，清空 `opener`，再跳站内 `/wallet-checkout/` 做 fresh payable 检查；被浏览器阻挡时显示安全的新标签页链接。不从浏览器返回、时间流逝或列表状态推断已付款。
- C2C 快捷区只展示购入、最多三笔进行中买单及完整页入口；支付／确认／出售等后续处理跳转到完整钱包，使用原订单 ID，不新增独立结算逻辑。
- 转出复用原报价、精确记账单位、确认与幂等请求。快捷弹窗的转出和 C2C 购入均使用内嵌确认，避免嵌套 native dialog 焦点锁。正常登录之外不增加资金验证码。
- 创建／转出／C2C 确认期间禁用任务切换、关闭及完整页链接；明确取消确认或操作完成后恢复。切换用户或退出时销毁私有弹窗和草稿，旧响应不得覆盖新账户。
- 手机端使用全屏弹窗，桌面限宽；焦点锁定及 Esc／焦点归还沿用 HeroUI。使用 Router 原主题 tokens，不更换全局字体或颜色。

## 文案与通知

余额发起方统一为「转出 / Send」，接收方为「转入 / Received」；链上转账、线下银行转账、付款证据等描述保留原义。收益和服务费邮件链接到收入标签，退租通知链接到原事项；金额、收件人、通知去重和英文邮件模板规则不变。

# Client Market 托管 Host 健康上报实施计划

**代码实施及本地整体 review 已完成，真实部署联合验收仍待执行。** 交付环境为新部署、使用同一健康协议 v1 的 Router 与 `cc-switch-server`。每台托管 Host 运行独立的 `cc-switch-server standby`，租期内与租户的 `serve` 并行。待机服务每个 UTC 自然小时随机择时，最多发起一次携带完整硬件快照的健康上报。买家在市场主行就能看到上报状态、时间和规格，并在报价中看到所选 Host 的快照。§8 保留实施顺序与验收门槛，§9 记录实施、验证和剩余环境验收；本地通过不等于 CI 或真实发布验收通过。

## 1. 背景与成本

实施前，供应商添加或导入 Host 后，Router 通过 SSH 验证机器，预下载所选 Server Release 并校验 SHA-256。准备状态 `ready` 只表示二进制已进入缓存。直到买家提交报价，Router 才安装正式 Client、初始化租户配置并启动进程。原有定期复查针对隔离和清理失败的 Host，空闲 Host 没有持续上报健康信息的来源。因此，两台同为“空闲、已准备”的 Host，一台可能刚刚可达，另一台可能已断联数天。买家也看不到它们实际可用的 CPU、内存和磁盘。[主机供给架构](../ARCHITECTURE.md)（§③）· [二进制准备](../src/client_market_binary.rs)（`prepare_queued`）· [隔离复查](../src/client_market.rs)（`reconcile_quarantined_host_reprobe`）

市场现有的 `clientConnection` 来自已绑定 Client 的隧道和 installation 心跳，只对有相应权限的用户展示。供应商的 30 天在线率汇总其已出租 Client 的样本。这两种数据分别回答“租户服务是否可连接”和“供应商整体表现如何”。买家选择具体 Host 时，还需要知道它最后一次何时上报、最近多少个小时按时上报，以及机器能提供多少资源。[市场连接状态](../src/client_market.rs)（`list_hosts`）· [供应商在线统计](../src/client_market_trade.rs)（`client_market_record_provider_daily_stats`）

采用同一发行物的独立待机服务，有两个直接收益。空闲 Host 无需创建租户、领取子域名或启动代理即可上报。出租后，即使租客停止或升级自己的 Client，市场仍能收到 Host 报告。代价是租期内多驻留一个轻量进程，其内存占用列入验收。正式 Client 已有的 installation 心跳默认约每 60 秒一次，承担 Client 在线判断和能力同步，继续走原协议。[Server 启动入口](https://github.com/Xiechengqi/cc-switch-server/blob/d8f813105f54efd540e76119350d004d2f1e4ef9/src/main.rs#L28) · [installation 心跳](https://github.com/Xiechengqi/cc-switch-server/blob/d8f813105f54efd540e76119350d004d2f1e4ef9/src/state/background.rs#L666)

10,000 台持续托管的 Host 每天最多主动发送 24 万份市场报告，平均约 2.78 请求/秒。保留 7 天明细对应最多 168 万条有效小时样本。现有 Client 控制面心跳另计。单个导入任务最多 100 台、5 个并发 SSH 操作，多个任务可以重叠。整点前集中就绪会压缩首报的分散时间，需要用多个导入任务实测秒级峰值。[批量导入](../src/client_market.rs)

## 2. 关键取舍

| 取舍 | 依据与实际影响 |
|---|---|
| 常规时刻在整小时 3,600 秒内分散，每小时至多一次应用层 POST | 断网、响应丢失、429 或 5xx 都等下一时段。客户端持久记录发包尝试，Router 用小时唯一键保证一次入库。 |
| 新 Host 在排程交付后随机 60–300 秒首报，可以跨整点 | 首报速率受安装吞吐约束（单个导入任务最多 100 台、5 并发 SSH），不会集中到整点前。若只在就绪所在小时的剩余时间内随机，整点前就绪时只剩几秒，而排程先于安装和启动交付，首报大概率落空并误报逾期，入市要多等一小时。 |
| 新登记的 Host 一律“本代有效首报后可租”；迁移前已入市的 Host 保留可租并自动接入 | 管理员或供应商可以看见准备中的机器。所有库存和报价入口都遵守同一准入条件。存量 Host 的兼容规则见 §7，代码合入主干后在已有数据的 Router 上也有确定行为。 |
| 买家可主动筛选或按健康排序，免费随机池沿用原有抽取方式 | 健康分层后依序取满会使低层 Host 在高层库存充足时完全失去被抽中的机会。本次交付目标是为买家提供选择依据。缺报或自报规格变化只影响展示。 |
| 租期内的成功与缺报同口径统计 | 24 个可观测时段缺 2 次显示 22/24。动态资源按采样所属租约授权，避免在退租后向市场公开上一任租客的负载。 |
| 完整报告区分已测值和未知值 | 只有能确定租户边界或数据卷时才展示对应容量。规格的可信度与小时报告是否按时送达分别显示。 |
| 密钥轮换与小时额度独立 | 经固定 SSH 指纹的登记和持钥证明切换凭据。已确认泄露立即撤销。租客有 root 时，自报来源可被控制，409 只能提供排查线索。 |
| v1 带版本标识、Router 先发布，待机服务识别带本代身份的明确撤销 | 出租中升级租户程序不影响待机进程，暂时无法识别版本或找不到 Host 时仍保留下一次排程。业务库不保存来源 IP。 |

保留的增强还包括“主机自报”标签、独立可执行副本、非 root 待机进程、轻量 runtime、8 KiB 报文上限、`machineEpoch`、按观察者裁剪的读模型、报价页采集告知，以及跨仓库共享协议样例。32 MiB RSS 作为测量目标，资源上限与守护参数按支持环境实测。

## 3. 排程与小时报告

| 场景 | 实施规则 |
|---|---|
| 常规时段 | `H = floor(unixSeconds / 3600)`，在 UTC 左闭右开区间内排程。取 `SHA-256("cc-switch-host-health/schedule/v1\n" + hostId + "\n" + decimal(H))` 的前八字节作无符号大端整数，对 3600 取模，得到秒偏移。使用 UTF-8 与 LF，`dueAt` 为该小时起点加偏移。`host-fixture` 在 H=4 的偏移为 3592 秒，即第 59 分 52 秒。 |
| 新 Host 首报 | Router 在交付排程时取 `firstDueAt = 当前时刻 + 随机 60–300 秒`，可以跨整点，首报归入 `firstDueAt` 所在的小时。两端持久保存同一排程，重复领取不能重抽。首报之前不按常规排程发送，首报取代该小时的常规报告，下一小时起使用散列时刻。任务交付排程即释放 SSH 和并发名额。待机服务对首个时段接受最多 4 分钟的晚启动（常规时段为 30 秒），留在 Router 5 分钟宽限之内，因此安装和启动的耗时不会让首报落空。 |
| 首报逾期 | 等到 `firstDueAt + 5 分钟` 仍未收到有效报告才显示逾期。若排程交付或进程恢复时已错过首个时段，跳过该次发送，之后第一个有效常规报告即可入市。例如，10:59:55 交付排程，首报落在 11:00:55–11:04:55 之间，归入 11 点时段。 |
| 最多一次 | 本机单实例。应用层发包前，在持久状态中原子记下稳定 `hostId` 已尝试 H，写入失败则跳过，写入后崩溃也算已尝试。HTTP 客户端禁用自动重试和重定向重发，恢复、租用、升级和凭据切换都不补包。在计划时刻前准备当次快照。短时 CPU 采样来不及时填未知。仅在所属小时发起发送，Router 的接收宽限不延长发送期。 |
| 接收窗口 | 首次写入取 Router 接收时间，窗口为 `[max(小时开始, dueAt − 2 分钟), dueAt + 5 分钟]`。首个时段使用 `firstDueAt`。窗口可跨整点，报告签名覆盖 H。相邻两次可以相隔 118 分钟（10:01、11:59），也可以只相隔几秒。 |
| 时钟异常与恢复 | 安装时用受信 Router UTC 与本次开机的单调时钟建立时间基准。发包前遇到墙钟跳变、重启后时间无法确认或偏差将使时段判断失真，暂停发包，先等宿主时间同步。空闲维护时也可经受信部署通道校时。校时不依赖再发一次健康 POST。异常恢复将校准时所在小时计为已用，下一时段照常排程。仅本次连接、与当前请求相符的可信响应可校正后续时间基准，迟到旧响应不能回拨排程。 |
| 尝试记录与乱序 | 持久保存已用时段，仅用已核实的 UTC 关闭历史时段并压缩为水位。误记的远未来 H 单独保留为已用，仅封住那一个 H，不能靠回退唯一的 `lastAttemptedHour` 来恢复。升级或重启保留记录。原状态丢失的同一 Host 按 §4 重新交付发送权。有效重复包只回既有确认，旧时段不覆盖新快照。 |

## 4. 托管生命周期与进程归属

`standby` 只读取托管配置、采集指标，并向 Router 建立出站 HTTPS 连接。它与租户 `serve` 使用不同的身份、服务名、配置目录和可执行路径。已验证的 Release 复制到稳定的托管路径，改名为 `cc-switch-host-standby`。`/proc/*/comm` 截断后为 `cc-switch-host-`，与租户 Client 不同，现有的进程名匹配不会命中它。服务命令必须显式带上 `standby` 子命令，因为 Server 无子命令时默认启动 `serve`。托管副本独立于会轮换的下载缓存和租户自更新路径。[Server CLI](https://github.com/Xiechengqi/cc-switch-server/blob/d8f813105f54efd540e76119350d004d2f1e4ef9/src/cli.rs#L171) · [二进制缓存](../src/client_market_binary.rs)（`prepare_command`）

| 阶段 | 行为与完成条件 |
|---|---|
| 登记与安装 | 单台新增、批量导入和显式换机复用 `onboarding` 与持久任务。沿用 SSH 身份和供应商归属检查。核验 Release 摘要及其 `version --json` 声明的报告版本，以已固定指纹的 SSH 连接登记 Host 本机生成的 Ed25519 公钥。安装任务持久记录排程并交给已就绪的本机服务，供应商看到等待首报。重启恢复未完成的交付沿用相同的机器代次、凭据与 `firstDueAt`。 |
| 首报开放库存 | 待首报的密钥仅能为本 Host、本代报送。首次满足 §5 的有效性要求时，在同一短事务内复核当前身份与阶段、保存小时事实和快照、激活登记并条件更新 `onboarding → idle`。删除、撤销、换机或过时任务不能使 Host 重新可租。部署失败可重试或撤销，已交付的同代排程随任务复用。 |
| 预留与提交 | 指定 Host 和随机池只从可租库存预留。预留、取消或 120 秒报价过期均不改排程。提交继续检查指纹、进程和安装绑定，规格变动仅提示可比字段。健康快照不参与定价、退款或远端清理。 |
| 已出租 | 待机服务继续上报完整快照。租户停止或升级正式 Client 时，仍由待机服务在下个计划时刻发包。租期内不因缺报经 SSH 进入租户环境。 |
| 清理与恢复 | 只清理已确认的租户安装，释放租约和账务结案仍走现有事务。租后入队幂等维护，校验副本、服务定义及 Release 版本，按需修复或升级。保存维护意图与执行权是两个步骤，只有成功取得空闲 Host 执行权的任务才能做远端改动。未获权时推迟到下个空闲期。维护三次失败后，已准入（或存量）且凭据未撤销的 Host 回到 `idle`，原上报器身份继续有效，6 小时后自动重试，供应商也可随时手动重试；仍待首报、换机中或凭据已撤销的 Host 留在库存之外。 |
| 轮换与撤销 | 新私钥在 Host 本机生成并暂存，受信 SSH 会话只取回新公钥和对一次性随机挑战的签名。Router 校验证明后，在事务中切换 `keyGeneration` 并撤销旧代，远端按同一操作序号启用新代。重启或回执丢失可恢复该步骤。普通轮换沿用原排程、尝试记录与历史，生效不依赖下一份小时报告。确认泄露时立即在 Router 撤销，并标记“需重新准入”：新代完成后 Host 回到 `onboarding`，收到新代的有效报告才重新可租；租中的远端修复等维护窗口。 |
| 换机与退役 | 确认物理换机才递增 `machineEpoch` 并撤销旧机，新代以 `onboarding` 重新入市，历史与 24 小时指标从新代起算。换机前为 `disabled` 或 `abnormal` 的 Host，新代首报后回到原状态，仍须供应商重新启用或经现有复查，不会直接变为可租。复用 `hostId` 前须确认旧服务已停用。旧机失联且无法确认时，退役旧 ID，实际更换的新机器按新 Host 登记。复用同一 ID 时，如旧发送方已经或可能获得本小时的发送权，即使 Router 未收到报告，也把本小时视为已用，新代在下一完整小时的常规时刻首报。退役先下架并撤销，归属确认后卸载。旧 PID 文件指向的进程已不是待机副本（重启或容器重启后 PID 被复用）时按过期处理，不阻断维护、换机和卸载。 |

**库存与并发。** 当前的准备触发器、reconcile 和 worker 只领取 `idle`。新增、批量导入都要让 `onboarding` 可以领取安装任务。盘点重验、报价取消或到期、开通回滚、退租清理等所有 `idle` 写入。数据库对插入或转入 `idle` 校验本机当前代已经准入且未退役，重验更新指纹时必须先判定是否换机。测试夹具按 `onboarding → 本代有效首报 → idle` 构造。供给摘要、供应商／国家计数、报价候选与预留使用同一可租条件，前端类型、按钮、分组和容量回退覆盖准备中与维护中。[准备触发器](../schema/0120_client_binary_preparation.sql) · [准备 worker](../src/client_market_binary.rs) · [重验与退租清理](../src/client_market.rs) · [容量回退](../frontend/components/dashboard/client-market/host-utils.ts)

维护领取与预留共用 Host 行的条件更新。维护必须满足本代、当前空闲、无绑定安装，原子取得 `idle → maintaining` 和持久任务号／递增操作序号。指定或随机报价竞争 `idle → reserved`。预留先赢则维护推迟，维护先赢则 Host 显示短时维护中。远端维护与开通在同一排他锁内核对机器、预期凭据代和操作序号，拒绝旧任务。在执行 SSH 前提交领取事务并释放数据库锁，完成时按领取的序号结案。Router 重启、任务超时或 SSH 中断后先确认远端动作结束或已被新序号隔离，再交回库存，不能只凭计时器释放。维护故障独立于上一笔退租和结算。现有 `binary:{hostId}` 只在进程内串行，报价直接条件更新数据库。[操作锁](../src/client_market_coordination.rs) · [二进制任务](../src/client_market_binary.rs) · [报价预留](../src/client_market_trade.rs)

**进程与恢复。** `cc-switch-server standby` 默认运行上报器，托管副本的服务命令显式使用 `cc-switch-host-standby standby run`。先解析 CLI，再为待机命令建单线程 runtime。配置、只供待机用户读取的私钥和可持久写入的状态分开，副本及服务定义由系统管理员持有。安装、停止、回滚、租户自更新及“远端已清理”的判断同时核对服务、路径、参数和归属，混合或未知进程保留现场。[现有 Server 启动入口](https://github.com/Xiechengqi/cc-switch-server/blob/d8f813105f54efd540e76119350d004d2f1e4ef9/src/main.rs#L8) · [现有进程清理](../src/client_market.rs) · [租户安装器](../install-client.sh)

systemd、OpenRC 以及有持久 PID 1 supervisor 或供应商启动入口的容器，要实测宿主重启后恢复待机。保留仅能 `nohup` 启动的 Host 的首报准入，标记为“未配置开机自启”，同时在供应商页、市场行和报价显示。对这类 Host 验收跨租用和跨租户 Client 启停持续上报，宿主重启后按实际缺报展示。所有守护方式均须遵守本代撤销标记。安装探测同时报告内核时间是否同步。未同步的 Host 首次上报靠安装时的 Router 时间基准，重启后要等时间同步确认才恢复发送，因此在供应商页、市场行和报价显示“未启用时间同步”。

## 5. 上报协议、采集与存储

**身份和验签。** 新增 `POST /v1/client-market/host-heartbeats`，登记为 `dashboard_machine_write_path`。HTTPS 请求体为 UTF-8 JSON，原始字节上限 8 KiB。v1 的五个头使用 `X-CC-Report-Version`、`X-CC-Host-Id`、`X-CC-Machine-Epoch`、`X-CC-Key-Generation`、`X-CC-Report-Signature`。前四项用于定位并与正文核对。签名输入为 UTF-8 域前缀 `cc-switch-host-health/report/v1\n` 加原始请求体的 32 字节 SHA-256 摘要，Ed25519 签名用无填充 base64url 编码。校验报文大小、已知协议、签名、身份和字段结构。验签及解析在业务数据库锁外，短写事务内重验当前绑定、撤销、时段和准入条件。主机 root 能控制自报值，SSH 执行同一采集程序的结果也标明来源。[机器写入分类](../src/api.rs) · [市场 SSH 授权](../src/client_market_terminal.rs)

**协议发布。** 首发两端只实现 v1，字段集固定。Server 的 `version --json` 增加 `hostHealthProtocolVersion`，Router 先发布接收能力，再选用声明支持该协议的 Server Release。安装和维护都校验该值。未知版本返回非终态诊断。新协议上线时另行安排仍在出租的版本和退场窗口。待机副本由 Router 在空闲维护窗口升级，租户自更新只作用于租户安装。[现有 BuildInfo](https://github.com/Xiechengqi/cc-switch-server/blob/d8f813105f54efd540e76119350d004d2f1e4ef9/src/build_info.rs#L37)

| 结果 | 服务与 Router 的约定 |
|---|---|
| 接受或幂等确认 | 当前有效绑定下，同一 `(hostId, utcHour)` 同一原始内容摘要返回 200。只对首次写入校验接收窗口，只写一条事实，重放不刷新接收时间、不重复上架。先验当前凭据，再给成功确认。 |
| 发送冲突 | 同一 `(hostId, utcHour)` 已有不同内容时保留首份，返回 `409 hour_conflict`。只对已认证且重复争用该时段的发送方记录有界诊断，区分已知交接与异常重复发送。409 是调查或轮换的线索。重复发送者可能来自克隆，Router 能保证最多接纳一份，本机单发送者约束见 §3。 |
| 其他失败 | 报文非法为 400、版本不支持为 `400 unsupported_report_version`、超限为 413、签名或绑定不符为 401、首次写入超窗为 422、限流或暂时故障为 429 或 5xx。待机服务记录有界诊断，等下一时段。由 Router 产生且能与本次请求关联的协议响应（含 422）携带 UTC `routerTime`，并回显 `utcHour` 和三项身份；四项均匹配当前请求才用于 §3 后续校时。 |
| 明确撤销 | `410 host_agent_revoked` 仅在验证原凭据并匹配撤销记录后发出，回显 `hostId`、`machineEpoch`、`keyGeneration`。待机服务再次比对当前本地绑定，三项都一致才写本代撤销标记并停用。删除业务 Host 后保留能识别原凭据的最小撤销记录。未知记录、普通 404 及迟到的旧代响应按非终态处理。 |

**有效报告与采集质量。** 正文必含 `reportVersion`、`hostId`、`machineEpoch`、`keyGeneration`、`utcHour`、`sampledAt`、`buildVersion` 和 `snapshot`。首次写入校验 UTC 时段、接收窗口及采样时间与计划的一致性，身份、系统和架构须有效。快照必须带齐下表所有字段。容量和负载无法证实时填 `null` 并附字段级原因（如 `scope_unverified`、`unavailable`），界面标明“规格部分未知”或“规格未确认”。缺字段、无效单位、越界数值或错误身份不能获成功确认。符合契约的完整快照即为有效报告，合法未知值同样返回 200 并可完成首次入市。

| 内容 | 采集口径 |
|---|---|
| `os`、`arch`、`effectiveVcpu` | 部署时记录实际环境和租户预期资源边界。对可确认的租户 cgroup、可见祖先、cpuset 和 CPU quota 取共同约束，保留小数 vCPU。支持 cgroup v1/v2，容器有 lxcfs 时核对其 `/proc` 视图。租户单元尚不存在时，需从可信部署配置确认将继承的限制。仅知道 `system.slice` 或待机服务自身的限额，不能推断租户的有效容量，无法证实时该项用 `null`。 |
| `memoryTotalBytes`、`memoryAvailableBytes` | 总量取已证实边界的有效限制与其可见内存的较小值，可用量同时考虑各级边界的用量和可见余量。字节用非负整数。用“宿主 64 核、租户限 0.5 核／512 MiB、待机另有限额”的夹具验证。[Server 已有 cgroup 处理](https://github.com/Xiechengqi/cc-switch-server/blob/d8f813105f54efd540e76119350d004d2f1e4ef9/src/self_update/upgrade.rs#L850) |
| `dataVolumeTotalBytes`、`dataVolumeAvailableBytes` | 在租户实际数据卷上取 `statvfs`，可用量使用非特权用户可用块数。部署时确认租户目标路径、挂载及可供非 root 读取的同卷测点，每次采集核对仍为同一挂载。即便能读取 `/root` 的容量，也需要证据确认 `/root/.cc-switch-server` 与之同卷。目标不可达、独立挂载无法验证、重挂载后身份变化时返回未知，无需放宽租户目录权限。 |
| `cpuUsagePct` | 对已确认边界的 CPU 计数做短时差分，按采样时长和有效 vCPU 归一化，按 0–100% 报送，短时突发达到或超过容量时记 100%。计数重置、边界或分母未知时按字段说明原因。若采样窗口跨越租约边界，动态指标按 §6 隐藏。 |

### 持久化与事务

- 托管登记保存 Host、机器代次、凭据代次与公钥、就绪及首次排程、已通过首报的代次、启动方式和撤销状态。维护任务使用可恢复的动作序号。换机结束旧代的统计区间。
- 小时明细唯一键为 `(hostId, utcHour)`。明细另存 `machineEpoch`、`keyGeneration`、原始内容摘要、Router 接收时间、采样时间、采集质量、最严格的可见范围及对应租约标识。密钥和机器代次均不增加小时额度。保留 7 天，按索引分批清理。
- 当前代的最新快照只随较新的有效 H 前进。有效首报、小时事实、当前快照与开放库存同事务提交。后续上报只更新健康数据。私有动态明细及最新快照中的同类值按 7 天到期，保留带原采集时间的最后静态规格和最近接收时刻。报价修订、租约时钟和业务状态的更新时间由原业务维护。
- 接收不可用区间、发送冲突诊断、最小撤销记录独立保存。按 `nextDeadline` 索引分批结算，每次任务可安全重跑。业务库不留来源 IP，按现有访问日志规则调查。[可信来源解析](../src/client_meta.rs)

| 状态 | 规则 |
|---|---|

| 平台观测中断 | 已有有效报告优先。在未收到时，仅 `dueAt` 落在已知接收中断区间（含容差）的时段标为平台未知，排除在分母外。 |

**接收不可用区间。** Router 按接收服务的就绪、正常停止和再次就绪记录区间，运行时每 10 秒记一次接收者存活刻度，崩溃后以最后刻度至恢复就绪近似估计，匹配 `dueAt` 时给 30 秒容差。接收者如有重叠运行，需确认全部不可用才据此排除时段。单进程记录无法定位 Cloudflare 或 Host 到 Router 链路的故障，未观察到服务中断仍计“Router 未收到”。平台原因未知时，界面不归因为 Host 物理离线。

24 小时指标取最近 24 个已到期的 UTC 自然小时时段，显示 **收到 /（收到 + 缺报）**。当前机器代从首个获准入市的报告时段算起，排除入市前、退役后和平台未知的时段。已接收但尚未截止的小时立即影响主行状态，到截止时才计入分母。租期内的成功和缺报对所有人同口径，24 个可观测时段缺 2 次即 **22/24**。样本少显示实际分母，分母为零显示“暂无可观测时段”。试用时长、履约收益、Client 连接及供应商 30 天统计各自使用原有依据。

列表批量读取摘要，只有打开详情才读取对应 Host 的小时历史。按计划截止时刻建索引，分批、幂等地处理到期项。中断恢复后可以补算历史状态，不要求 Host 补发。可以用缓存降低读负载，但必须能用小时事实与接收不可用区间重建摘要。批量导入、接收高峰和报价并发时测量锁等待，再决定是否需要位图等优化。

**选择 Host。** 买家可以按上报状态、近期记录和可比较的静态规格筛选列表或排序。免费随机报价在已有供应商、地区、市场访问及免费额度条件后，对全部可租候选打乱取样。低健康记录仍有抽中机会，选中的每台 Host 都在报价项显示同一健康摘要。[随机报价](../src/client_market_trade.rs)

## 7. 首版部署与存量 Host

Router 和 Server 配套部署。先发布带待机能力（`version --json` 声明 `hostHealthProtocolVersion: 1`）的 Server Release，并让 Router 选定它，再部署接收 v1 的 Router；否则所有新 Host 的安装会被版本检查拒绝。远端版本不符时把原因留在供应商部署诊断中。

代码合入主干后，已有数据的 Router 升级时同样执行迁移 124，因此迁移对存量 Host 有确定行为：

- **登记。** 为每台现有 Host 建立健康登记，标记为“存量”，并排入待机安装队列。迁移本身不改 Host 状态、租约、订单和账务，也不发起远端操作。
- **可租。** 存量标记等同已准入：空闲的存量 Host 继续可租，退租、报价取消或到期后照常回到 `idle`。首份有效报告到达时清除标记，此后与新 Host 完全一致。
- **接入。** 空闲的存量 Host 由后台维护任务自动安装待机服务，安装期间短时显示维护中。已出租且尚未首报的存量 Host 可走 §10 的独立首次监测接入任务，不必等待退租；常规升级、轮换和换机仍在退租清理后执行。空闲维护安装三次失败时回到 `idle`，6 小时后重试（§4）。
- **历史租约。** 迁移把现有租约写入持久租用区间，供样本的租约归属和隐私裁剪使用。

验证从空库完整建库，并在含历史订单、租约和账务的库副本上核对迁移不改写这些数据。[Router 迁移入口](../src/schema.rs)

## 10. 已出租存量 Host 接入修复与市场界面优化

### 10.1 背景与线上根因

2026-11-23 对 `sgptokenswitch` 只读核查时，Router 已运行 `7fabcd6`，迁移 124 已生效，接收观测循环存活。3 台 Host 均处于 `allocated`，已绑定有效租约，但健康登记仍为 `legacy=1`，公钥、首次排程和硬件快照为空；准备队列均为 `pending`、尝试次数 0。原 worker 只领取没有安装绑定的 `onboarding/idle/maintaining` 主机，因此长期租用、尤其永久免费租约不会获得监测接入机会。旧摘要把空登记显示为“等待首报”，掩盖了从未安装上报器的实际情况。

截图还暴露了展示问题：健康文案、未知说明和详情入口集中堆在第一列，硬件没有独立位置；两套排序彼此竞争，容量条件常驻工具栏撑高页面，展开历史会继续撑大行高。单纯重新发布 Server 无法解决上述队列资格和展示问题。

### 10.2 已实现的任务边界

新增迁移 125，不修改已经部署的迁移 124。增加独立首次监测接入表及部署 commit／时间字段，迁移本身不修改存量租约、账务、主机状态、密钥或排程，也不自动执行 SSH。

| 入口／状态 | 行为 |
|---|---|
| Host owner 的健康抽屉、选中主机批量接入 | 调用严格的 `/health/bootstrap` 请求，固定 `expectedInstallationId` 和 `expectedMachineEpoch`；浏览器批量请求并发最多 3。 |
| 部署运维 | `cc-switch-router host-health bootstrap --host-id ID --expected-installation-id ID --expected-machine-epoch N [--env-file PATH]` 经现有 UID 认证的本机 socket 入队，不离线写库。 |
| 领取与执行 | 仅处理已出租、有效租约、尚未首报的存量主机；没有撤销、换机、重新准入、轮换或开通任务。已有公钥只允许原上下文恢复。同一 Host 单任务，共享现有 SSH 并发限制和远端锁。 |
| 上下文变化 | 固定租约、机器代次、密钥代次及动作序号；每个阶段复核。退租、换绑和身份变化取消旧任务；owner 发起的任务还受 owner 变更约束，运维发起的任务仍受租约和机器约束。 |
| 失败恢复 | 自动重试间隔 15 分钟、最多 3 次；最后一次尝试中断超时后转为失败，可显式重试。过期上下文任务移出队列，避免占住后续领取名额。 |
| 远端操作 | 先校验既有监测配置身份，再停止或更新独立待机副本；不替换、不重启租户 `serve`，不执行包管理器，不改动租用状态、合同和账务。 |
| 小时约束 | 同代重试保留密钥和已交付首报排程；安装、probe 不上报、不补发，不突破每 Host 每 UTC 自然小时至多一次主动 POST。 |

这条路径仅解决“从未接入监测”的已出租存量主机，常规升级、轮换及换机继续走空闲维护。Server 现有 v1 待机能力足够，本轮不修改 Server 仓库。

### 10.3 展示及隐私

## 1. 目标、决策与边界

目标是把 Share Market、Client Market 的付费流统一为「用户向平台充值 → 全站钱包支付 → Provider 按履约获得收入 → 沉淀至少七天 → Provider 申请提现 → Router Owner 线下付款」。用户不再给每个 Provider 单独充值，也不再为了租用一项服务配置某个 Provider 的收款信息。

已确定的产品决策：

1. 首版只有一个 USD 计价的钱包资产；同一用户在两个 Market 和所有 Provider 间共用。钱包归属使用 Router `user_id`，不使用邮箱、Provider 昵称或可变化的公开别名。首版不把其他游戏币或支付资产与 USD 混合；日后增加资产必须创建独立账本和明确兑换契约。
2. 充值渠道由 Router 内置。Owner 在 Settings 可配置并同时启用多个渠道，首个适配器为 DujiaoPay；多个渠道订单与密钥隔离，但成功充值进入同一个用户钱包。
3. DujiaoPay 首版使用托管收银台模式：Router 以固定商户订单号创建支付单，用户在收银台选择链和币种。Router 不要求用户输入 Binance UID，不伪造一个可由 Binance 自动识别收款人的二维码。固定链/币下单作为以后可加的渠道模式，不妨碍当前表结构。
4. Market 首版不继续向用户开放 Provider 专属预存、Provider 授信、账单付款声明或商家确认收款作为付费购买手段。免费供给、试用、商品准入、Provider Rank、服务控制和合同完整性校验仍保留。
5. 平台钱包扣款不是 Provider 立即获得可提现款。固定月租先记「未履约款」；按秒服务只对可计费履约时间扣款。形成 Provider 收入的每一份，最早在 `max(buyer_debited_at, fulfilled_at) + 604800 秒` 转为可提现。所有时间使用 UTC。
6. 买家消费按商品原售价扣款，不另加消费手续费；充值按用户希望到账的本金另加维护费，默认 5%，Owner 可设置 0–100%（精度 0.01 个百分点）。例如填写 10 美元，到账 10 美元，维护费 0.50 美元，向网关支付 10.50 美元。金额与政策版本在报价和订单内冻结；渠道费率仍只是网关成本估算，不能与用户维护费混淆。Provider 从已履约收入中承担的独立平台服务费见 §16，不增加买家商品售价。
7. Provider 首版提现资产为指定网络的 USDT，面额按 `1 USD 账面金额 = 1 USDT 名义转账金额` 处理，网络费由 Owner 承担。Owner 线下实际转账，Router 不掌握出款私钥，也不调用 DujiaoPay 出款。其他币种、银行账户和动态汇率不是首版范围，扩展时须增加「报价—接受」步骤，不能把汇差藏进现有提现记录。
8. 消费余额不支持提现或自助外部退款。用户可免费即时转给本 Router 中已验证且有效的其他用户；不得转给自己、未注册邮箱或转成 Provider 收入。未付款取消、服务退款回余额、外部退款／拒付冲正不受此限制；它们不是消费余额提现。DujiaoPay 返回页或 `refund.recorded` 事件都不等于已完成 Router 记账。
9. 不做旧财务数据迁移、不双写旧账本，也不把旧商家专属余额解释为新钱包余额。新资金域按新合同验收；旧迁移文件保持不可变，旧付费写入口在最终切换时退役。需要原位承接旧余额的运营环境不属于本计划。

## 3. 核心不变量与金额精度

- 每笔账务事件由一笔不可变 journal transaction 和至少两笔 posting 表达；同一 journal 内、同一资产的带符号 posting 之和恒为零。修改历史只允许新建冲正或调整流水，不 `UPDATE` 已记账金额。
- 用户钱包 `posted_units >= held_units >= 0`，`available_units = posted_units - held_units`；hold 的建立／释放要在 journal 内表达用户可用与冻结逻辑账户之间的转移，缓存与 hold 明细同事务更新。扣费、退款和提现申请均在 `IMMEDIATE` 事务内用条件更新或等价 CAS 防止超支。
- 保留 Router 现有整数精度：`1 USD cent = 86400 money units`。DujiaoPay 的 USD 十进制字符串必须先精确解析为美分，再乘以 86400 入账，例如 `1.00 USD = 100 × 86400 = 8640000 units`；拒绝超过两位小数或溢出的面额。按秒费率用整数及 `i128` 中间计算。任何前端展示取整都不能反向影响账本。Provider 提现只转出完整美分；不足一分的剩余单位留在原账户，不能抹掉。邮箱“转出全部”保留每一个记账单位，禁止先取整再转账。
- 充值、合同开通、按秒扣费、月租续费、服务退款、收入确认、收入解锁、提现申请和付款登记分别使用独立的、带主体作用域的幂等键。相同键加相同请求指纹返回旧结果；相同键加不同指纹返回冲突。
- 任何 Provider 收入必须引用一笔已入账的买家扣款以及可核对的 Share／Client 合同与履约证据；绝不能仅凭「服务处于 active」或「充值成功」生成 Provider 收入。
- 任何 Provider 的可提现额不得超过其已确认履约收入减去冲正、退款、争议冻结、已申请提现和已付款。用户钱包余额、未履约款、Provider 待解锁／可提现／提现中金额与平台费用必须能逐笔从 journal 重算。
- 公开 API 不返回钱包余额、合同财务明细、提现地址、支付商户密钥或真实用户身份；资金 API 一律按 Session user ID 或 Owner 权限过滤并设置 `Cache-Control: private, no-store`。

首版 journal 是 **USD 计价的资金义务子账本**，不是 DujiaoPay 收到的链上币种库存账。约定 journal 的借方为正、贷方为负；负债类账户在贷方增加，余额投影则以正数展示。`Owner 清算桥` 是每笔入金、出金的 USD 计价对手账户，不宣称 Owner 实际持有等量 USD；真实收币、换币、费用和出币须用外部流水另行对账。最低过账模板如下，所有行必须同事务写入 journal、幂等来源和对应投影：

| 事件 | 借方 | 贷方 |
| --- | --- | --- |
| 已核验的充值 | Owner 清算桥（实付） | 买家钱包可用负债（本金）＋平台维护费收入 |
| 购买冻结／解除冻结 | 买家钱包可用／冻结负债 | 买家钱包冻结／可用负债 |
| 月租当期捕获 | 买家钱包冻结负债 | 月租未履约负债 |
| 按秒服务捕获 | 买家钱包冻结负债 | Provider 待解锁负债 |
| 月租履约片段 | 月租未履约负债 | Provider 待解锁负债 |
| 七天成熟 | Provider 待解锁负债 | Provider 可提现负债 |
| 提现申请／拒绝退回 | Provider 可提现／提现冻结负债 | Provider 提现冻结／可提现负债 |
| 提现线下付款登记 | Provider 提现冻结负债 | Owner 清算桥 |
| 邮箱转账 | 发送钱包可用负债 | 接收钱包可用负债 |
| 外部充值退款冲正 | 原买家可用余额＋平台费用冲回＋Owner 损失（若有） | Owner 清算桥 |

服务退款以原收入所在的未履约、待解锁、可提现或提现冻结账户为借方，以买家钱包为贷方；先冻结争议份额，再在不超过尚未线下付出金额的范围内冲正。已经实付的部分另记 Owner 对 Provider 的追偿或损失，不允许把原提现 journal 改写成未付款。`posted_units` 是该用户钱包可用与冻结负债的合计正数投影，移动 hold 不改变它。

## 4. 数据模型与迁移

从 `schema/0053_market_platform_wallet.sql` 开始新增迁移，并在 `src/schema.rs` 登记。名称仅作为实施建议；若实施前已有新迁移，以届时下一个版本号为准。旧 migration 不改写。先以外键、`CHECK`、唯一约束和索引表达可落在数据库层的约束；业务事务再校验跨表守恒。

| 新表／对象 | 必备字段及约束 |
| --- | --- |
| `market_wallet_accounts` | `user_id, asset_code` 唯一；`posted_units, held_units, version` 非负；首版只允许 `USD`。 |
| `market_journal_transactions`、`market_journal_postings` | 全局唯一 `source_kind, source_id, action` 或等价幂等键；posting 含逻辑账户、主体、资产、带符号整数单位、创建时间；journal 提交前验证同资产净额为零。 |
| `market_wallet_holds` | 用户、合同／报价／退款来源、金额、用途、状态、到期时间、版本；同一业务来源只允许一个活动 hold。 |

| `market_delivery_slices`、`market_provider_earning_lots` | 合同、服务有效时间段、原始计费来源、扣款 journal、Provider `user_id`、收入单位、冲正单位、`fulfilled_at`、`unlock_at`；来源片段唯一。月租片段另引用期间 ID。 |
| `market_usage_posting_batches` | 按合同和有界时间窗归并已持久化的按秒 accrual；起止游标、总单位、journal ID 唯一，便于补偿重放。 |
| `market_payout_destinations`、`market_payout_requests`、`market_payout_allocations` | Provider 归属、网络与地址、地址版本／快照、申请金额、状态、Owner、外部转账流水号；一份 earning lot 不可超额分配。 |
| `market_buyer_refund_requests` | 用户、钱包 hold、金额、收款地址快照、状态、Owner、外部转账流水号；只能冻结可用余额。 |
| `market_finance_reconciliation_cases`、`market_finance_audit_events` | 异常代码、对象、处理状态、操作者和时间；不得把 Secret 或完整支付 body 写入审计 JSON。 |

逻辑账户至少有：Owner 收款待清算、用户钱包负债、用户钱包冻结、月租未履约款、Provider 待解锁应付、Provider 可提现应付、提现冻结应付、平台费用／损失及异常待核对。余额缓存是 journal 的投影，必须有可独立重算的对账器；不能把缓存作为唯一资金证据。

Provider 金融归属固定为交易发生时的 `supplier_user_id`，公开 `market_provider_id` 仅用于展示和身份发现。Provider 换邮箱、改展示名或发生公开身份合并，不能重指向历史提现权；身份冲突时停止新收入释放和提现，进入 Owner 对账。

## 5. DujiaoPay 渠道契约

### 5.1 配置与启用

Settings 的 Marketplace 分类提供独立「充值渠道」面板及专用 Owner API。每条渠道可设置展示名、API Key ID、API Secret 和 Webhook 签名密钥；保存时先用 `whoami` 验证商户 API，渠道初始关闭。固定回调地址 `https://<Router 公共域名>/v1/payment-webhooks/dujiaopay` 在建渠道之前即可复制并配置；不能要求先取得渠道 ID。实际地址由 Router 可信域名配置生成，不接收浏览器提供的目标 URL。API Base 在正式环境固定为受信任的 HTTPS 官方主机，仅测试允许 loopback。

适配器实现 `GET /v1/whoami` 商户身份验证、`POST /v1/orders` 建单及 `GET /v1/orders/{id}` 查单。API 请求使用独立 API Secret 签名。DujiaoPay 官方控制台创建 Webhook 后生成独立签名密钥，只显示一次；不能填假值或复用 API Secret。新渠道默认 `signed`，使用原始 body HMAC 验签；无密钥时只有 Owner 明确选择 `poll_only` 才能配置：无签名回调只可按已存在的随机商户单号唤醒查单，不能直接改变订单状态或入账。既有 revision 迁移后默认保持 `signed`，原带渠道 ID 的回调地址继续有效；替换既有签名渠道时不允许默默清空 Secret 或降级。具体字段、`paid_source` 枚举、USD 商户支持及回跳 URL 仍须以真实商户受控联调锁定，不能只凭参考项目 fixture 声称已验证。

启用顺序：先在商户后台设置固定回调 URL 并保存只显示一次的签名密钥 → 保存加密的 API／Webhook 配置并通过 `whoami` 冻结商户身份 → 用受控最小金额真实 USD 收款验证签名回调、建单、查单、链上回执及钱包入账 → Owner 明确启用。`whoami` 成功只代表 API 凭据有效，不代表 Webhook 或真实充值已验收。资料编辑只递增渠道版本；API 与 Webhook 密钥轮换各产生新 revision、停止新单且不得跨商户。未终结订单保留旧 revision 的交易身份及允许支付方式；已知网关订单优先用同商户当前 API 密钥查单，失败时只读回退旧密钥，以兼容新密钥吊销旧密钥或网关按密钥隔离历史订单。创建结果不明的旧订单只用原建单密钥重试同一商户单号，避免跨密钥重复建单；若原密钥已失效，须人工对账。旧 revision 仍须可解密；无法解密时停止自动入账并告警，不降级明文或信任浏览器状态。

Owner 若确需把既有签名渠道改为仅查单，须使用更换回调密钥 API 显式提交 `webhookMode: "poll_only"`；只省略 Secret 会被拒绝。恢复签名模式须提供新 Secret 和 `webhookMode: "signed"`。签名验签使用同一商户渠道的当前回调密钥，不依赖旧订单的 API revision；普通轮换可短暂接受前一个签名密钥 10 分钟，紧急轮换立即撤销。降级 `poll_only` 后，固定及旧带渠道 ID 的回调都只能唤醒认证查单。归档只停新单，不删除渠道或订单；归档也立即撤销上一回调密钥的过渡期，旧订单仍由当前签名密钥或认证查单处理。恢复后仍保持停用，并须通过 Owner 的 `verify` API 重新验证现有商户 API，或轮换为同商户的新密钥，才能再次启用。归档／恢复也清除旧回调验证状态，新的签名回调需重新证明。固定地址可接受不含订单号的商户后台测试通知，但不会将其视为支付证据或签名验证通过。

渠道启用采用试运行（canary）：启用后当前 revision 进入 `canary`，只有 Router Owner 能用它充值，普通买家看不到；当前 revision 首笔严格验真入账（生产模式下还需当前 revision 的签名回调已验证，可由商户后台的 `webhook.test` 签名事件证明）在同一事务内自动把渠道转为 `live` 并告警 Owner。轮换、整体替换、归档恢复后渠道回到 `off`，重新启用即重新试运行。迁移 81–82 后 Owner 可关闭官方充值或退回影子测试；重新开放仍检查当前 revision 的真实入账及签名证据，不沿用旧批准绕过门禁。模式变化不影响余额消费、转账、C2C 或既有订单对账，也不恢复旧 Provider 付款轨道。

### 5.2 充值状态机

`created → creating → pending → verifying → credited` 是正常路径；另有 `create_unknown`、`expired`、`cancelled`、`review_required`。`credited` 为终态，不允许后到的过期或取消回调降级。`expired/cancelled` 后真实链上到账不能丢失：严格匹配成功则入账一次，无法严格匹配则进入人工核对。`create_unknown` 表示建单请求超时且不能证明上游没有建单，必须以原 `merchant_order_id` 和相同请求体／幂等键重试，不能生成第二个应付订单。

创建顺序：

1. 鉴权、限流、校验 USD 金额上下限与渠道启用状态；用浏览器幂等键和请求指纹在本地事务中先写订单及配置 revision。金额一经创建不变。
2. 事务外签名调用网关，优先选择托管收银台；仅保存同一订单的 `order_id`、`checkout_url` 与过期时间。返回的收银台 URL 必须为允许的官方 HTTPS origin，拒绝任意跳转地址。网关调用绝不在 Router 数据库 mutex／事务内进行。
3. 若网关调用超时或更新本地订单失败，保留 `create_unknown`，由补偿任务用同一商户单号重试／查单。Webhook 可能先于建单响应到达，因此应能先按已存在的 `merchant_order_id + channel_revision` 定位本地订单，待网关 ID 补齐后再次核对。
4. 浏览器回跳只显示「付款核对中」；状态由 Router 私有查询 API 获取，绝不由 `success_url`、前端轮询次数或截图决定入账。

固定 URL 对无签名渠道只解析格式受限的 `merchant_order_id`，用本地唯一订单绑定找到原渠道 revision，并在持久化的单订单五分钟冷却下提前安排一次查单；不保存通知宣称的支付状态、金额或网关订单 ID，也不由请求线程直接查询网关或记账。签名渠道使用当前或短暂过渡的回调密钥 HMAC 校验和事件审计，固定 URL 与旧带渠道 ID 的 URL 均可使用。两种模式真正入账均依赖事务外 `GET /v1/orders/{id}` 的认证响应，并在 `IMMEDIATE` 事务内核对渠道／商户、双重订单 ID、USD 面额、`paid_source=chain`、链上回执和唯一性。网关暂不可用时保留持久化重试时间，不能把通知当作收款证明；证据冲突则进入 Owner 复核。`refund.recorded` 只作为外部记录信号，不自动扣除钱包或认定线下退款完成。

回调路由无用户 Session；固定 URL 的无签名内容始终不可信，限流、64 KiB body 上限、单订单冷却和最多 24 单／轮查单预算是其资源边界。所有未入账状态按年龄退避，并在创建后 90 天内定期查单；窗口结束后仍可被回调唤醒。超过窗口且没有回调的迟到付款不能自动发现，须以 Owner 对账处理，不能宣称零漏账。全局 IP blacklist 对两个精确回调路径豁免，但不豁免限流或签名渠道验签。不得在日志、前端错误或告警正文输出 Secret、签名头、原始失败 body 或完整支付资料。

无签名通知中的退款字段同样不能直接认定为退款，也不会生成可信退款审计；Owner 必须用商户后台与外部收款流水独立对账。

超过 90 天的旧订单收到通知后仍会开启最长六小时的持久化查单恢复窗：网关暂不可用时五分钟后重试，未付款则限频复查，窗口结束后停止。无通知且无外部对账时无法证明“绝无漏账”。

## 6. Market 扣费、履约与退款

### 6.1 报价及购买

Share 与 Client 的 quote 返回不可变报价快照：商品和 Provider `user_id`、商品修订、价格、计费模型、有效期、钱包可用额、被已有服务占用额、当前订单最小差额。新订单提交前仍复核在线／库存／授权／价格／身份和报价指纹。

钱包不足时显示「充值差额」，保留商品上下文；充值到账后重新报价，用户再明确确认，不自动复用过期报价或自动下单。报价查询不冻结余额。提交时在同一 `IMMEDIATE` 事务内冻结开通所需金额并创建待激活合同；Provisioning／Share 授权成功时捕获当期款。失败时必须先确认授权／Host 清理已完成，才能释放全部 hold；外部状态不确定时保留冻结并进入恢复或人工复核，不能退款后留下仍可使用的服务。相同报价重试不会重复建服务或扣款。免费和试用订单不创建付费 hold。

### 6.2 按秒服务

现有 Market reconcile 频率较高，不应把每次健康检查都扩展为多笔复式财务流水。保留逐段服务间隔／accrual 作为履约证据；以有界批次（目标约一分钟，具体用性能测试定上限）按合同、账期顺序汇总并过账。批次包含闭开时间窗与最后处理的 accrual 游标，重试不重复扣款。活跃服务从钱包预留约 24 小时的预算，已激活服务的预算优先于新订单；每次批量过账同时减少 posted 与相应 hold，再尝试补足滚动预算。余额不足时只记已被资金覆盖的履约时间，按现有控制链路暂停对应服务，不能产生平台负余额或隐形 Provider 信用。

当多个服务共用钱包且不足以全部补足时，先兑现现有 hold，再按到期时间、既有 `renewal_priority`、合同 ID 的稳定顺序分配；结果必须可重放、可审计，并在用户界面标出可能暂停的合同，不能让 HashMap 遍历顺序或 worker 抢锁顺序决定谁先得款。

### 6.3 固定日历月租

开通或续期只扣当前服务期款，不再强制预留下一整期。自动续期到期时以当时的钱包余额原子扣款；不足则进入现有 recovery／暂停控制链路，提前提醒但不静默借用 Provider 授信。试用转付费按实际开始时间建立第一服务期。用户选择「到期取消」则不扣下一期。

当期扣款进入「未履约款」，不立即生成 Provider 可提现额。以半开服务区间 `[period_start, period_end)` 的可用服务时间生成履约片段，按 `i128` 整数比例分配当期总单位；最终片段吸收整数余数，保证片段总额、自动退回金额与当期扣款完全相等。这里的履约指合同约定的可用服务，不要求用户必须向模型发起请求。可核实的停服／合同完整性故障不计 Provider 履约；未履约余额按现有合同规则退回用户钱包，期末不能永久挂在未履约账户。Provider 提前终止、开通失败、价格变更和争议均先冲正未解锁收入，再决定是否冻结已解锁但未付款收入。

### 6.4 退款、争议和收入逆转

服务退款回原平台钱包，不回某个 Provider 专属账户；同时冲减同一合同的未履约款或未付 Provider 应收。争议发生时，冻结相关 earning lot、暂停提现申请；确认后以新的冲正 journal 调整，不修改历史 lot 金额。若对应款项已进入提现或线下转账状态，须先确认外部转账未发生，才可从提现冻结款退款；转账结果不明时保持隔离待对账，不能同时退款和继续付款。若对应款项已线下转出，则记录 Provider 应收回款或 Owner 损失，不能制造负用户钱包，也不能用别的 Provider 余额掩盖。普通用户不能新增余额外部退款。历史已产生的外部退款义务仅保留审计与完成处置，不在用户界面重新开放申请。

## 7. Provider 收入与线下提现

每笔收入 lot 固定 `buyer_debited_at`、`fulfilled_at`、`unlock_at`、Provider `user_id`、合同和扣款来源。定时任务仅把未争议且未冲正的成熟份额从「沉淀中」转到「可提现」；重复运行、时钟回拨和服务退款并发不能重复解锁。月租首日收到的钱最早是首段服务履约完成七天后逐步解锁，不是整月扣款后七天一次性解锁。

Provider 在账户页保存网络、资产和地址；地址变更需二次确认、版本化并有 24 小时冷静期，已提交提现申请永远引用旧地址快照。提现申请从可提现 lot 按 `unlock_at, lot_id` 稳定顺序分配，原子转为冻结；重复点击返回同一申请。Owner 审核后线下转账，先把申请从 `approved` 标为 `transfer_in_progress` 并锁住退款／拒绝操作，再填写链上交易 ID、转账时间、资产、网络和实际到账名义金额；系统核对名义额与申请额及外部流水号唯一性才标记 `paid`。正常路径为 `requested → approved → transfer_in_progress → paid`；仅确认**未发生外部转账**时，才可从 `requested/approved` 拒绝并解冻，或把失败转账转为 `transfer_failed` 后重新批准／拒绝。结果不明进入 `review_required`，保留冻结，不可自动重发或解冻。每一步都记录操作者与版本；`paid` 不允许撤回或再次付款。Router 不能自动确认外部链上到账，因此「Owner 标记已付」是人工审计声明，UI 要明确这一点。

### 7.1 运营方偿付与对账

Owner 收到的是 DujiaoPay 商户实际入金资产，Router 给出的却是 USD 计价钱包负债；两者不能因一笔网关回调就被视为同一资产。必须每日对照网关已付款订单、收款账户流水、用户钱包负债、月租未履约款、Provider 未付款应付、用户退款冻结和 Owner 已转出凭证。网关费用、资产转换损益和转账网络费独立入账，不改用户或 Provider 名义金额。对账差额、缺少外部付款凭证、已付标记但未知转账流水、已收款但未入账、负值或跨主体引用均创建 Owner 待处理 case 并暂停受影响渠道或提现。

用户界面只有四个购买重点：商品与周期价格、全站可用余额、需充值差额、主操作「确认租用／充值差额」。不显示 Provider UID、尾差、账单声明或多个分割区。充值结束返回原商品卡并刷新报价；未成功就保持「等待到账／人工核对」，不显示假成功。账户新增全站钱包和充值流水；Provider 收入／提现独立面板；Settings 的 Marketplace 分类增加 Owner 充值渠道与财务状态面板。原 Provider 页中预存／信用汇总与按 Provider 充值入口删除或替换，Provider 排名算法及公开质量数据不受钱包改造影响。

## 9. 安全、异常和停机策略

- DujiaoPay API/Webhook 密钥使用独立于 Binance 的主密钥和 AEAD 加密，AAD 绑定渠道 ID、商户身份和 revision；密钥文件／环境 Secret 与数据库分开备份。错 key 或 key version 必须 fail closed，不回退明文。参考 `src/binance_settlement/crypto.rs` 的封装思想，但新支付模块使用独立密钥域。
- 只有 Owner 可改渠道、审批出款或处理人工入账；「人工确认已付款」必须写明外部证据、金额、来源和理由，不能仅凭签名 `order.paid` 中的人工 `paid_source` 自动记账。审计可以记录摘要／稳定错误码，不记录签名头、API Secret 和原始失败 body。
- 财务模式有 `disabled / shadow / enabled` 切换门禁及单渠道开关。`shadow` 仅允许 Owner 测试充值；`enabled` 仅在 Owner API 通过真实入账和切换门禁后开放，批准后不可退回旧支付轨道。生产异常使用独立的「暂停新钱包订单／新提现」开关；关闭渠道可停止新充值。暂停不阻止既有合同履行、已发起出款的结果登记、服务退款回余额、Webhook 或对账，也不抹掉 pending 充值订单；已经付的钱仍须查单和核对。配置页明确区分 API 验证、签名回调验证及当前 revision 的真实入账，不能把空订单号测试投递误记为通过。
- 支付网关或 Turso 不可达时停止新建单／扣费的相应写入；签名 Webhook 事件和无签名回调唤醒的查单时间表持久化，网关恢复后重试。数据库事务内不发外部 HTTP。Router 当前 Turso 模式仅支持一个可写实例，本计划不引入多主写入或离线写。
- 设定金额上下限、用户及 IP 建单速率、单用户 pending 订单上限、Webhook body 上限、外部 HTTP 超时与退避、健康告警和补偿任务预算。无渠道可用时明确提示，不能退回旧商家直付链接。
- 对账异常、Secret 解密失败、网关身份变化、连续查单失败、零和不变量破坏、重复外部转账参考号等需要可观测的 Owner 告警。资金不变量失败时冻结受影响资金路径，而不是尝试用调整 SQL 自动修复。
- 投产前冻结每个渠道经真实商户验证的最小／最大充值额、同时待付订单数、建单节流和提现最低额；不得把网关不支持的低额订单开放给用户，也不得以默默提高付款额的方式满足渠道下限。地址冷静期和七天收入沉淀是独立计时器，不能互相替代。

## 12. 非目标与后续扩展

本期不处理旧余额迁移、合规评估、DujiaoPay 出款、Provider 自动提现、多资产钱包、自动 FX 出款、额外向买家收取消费佣金或买家从多个资金源拆单支付。Provider 侧服务费已在 §16 纳入范围。以上能力均有明确扩展点，但不能为了预留它们削弱首版同资产零和、来源核验或七天沉淀约束。完成定义是资金可以逐笔对平且所有失败路径可恢复；「能跳到收银台并看到成功页」不构成完成。

## 13. Owner 影子验收与切换清单

1. 先备份 Router 数据库及支付密钥，部署迁移但保持 `disabled`。确认 `/v1/admin/market-finance/readiness` 的 `codeIntegrated`、旧域 blocker、严重对账 case 与渠道 blocker；不可用手改数据库模式替代 Owner API。首次启用后切换批准永久保留，不能再切回 `shadow`／`disabled`；应使用独立的暂停开关处置事故。
2. 在 DujiaoPay 官方商户后台配置 Router 固定 Webhook URL，保存只显示一次的 Webhook 签名密钥。Router 渠道 API 验证、Webhook 验签和真实入账是三个独立证据；`whoami` 通过不等于后两者通过。商户必须实际支持以 USD 两位小数建单和可认证的支付来源。
3. 切到 `shadow`，仅由 Owner 以受控最小 USD 金额完成一次真实支付，保留脱敏订单号、官方查单状态、签名回调时间、链上回执和 journal 对账结果。另验证重复／迟到 Webhook、查单短暂失败和回跳不会重复入账。不能把 fixture、测试通知或浏览器成功页计作真实收款。
4. 在旧路径清结并撤下所有付费旧商品和活动报价，核对旧合同、余额、hold、欠款、退款、争议、待确认充值均为零。保持 `shadow` 且 `readiness.canEnable` 为真时，Owner 才可通过 API 切到 `enabled`；不能从 `disabled` 跳过影子验收。之后 Provider 按钱包规则逐项重新发布付费 Share seat 与 Client Host。
5. 小范围验收充值→报价→冻结→开通→履约→争议／退款、资金不足暂停、七天后提现申请→Owner 线下转账登记。每一步对比钱包、未履约、Provider 待解锁／可提现／提现中与 journal 零和。发现严重不变量或网关身份异常，使用 Owner 暂停开关立即停新钱包单与新提现，必要时关闭渠道停止新充值；继续收取并核对已发生支付的回调，已有合同照常履行。已有真实入账时只能向前修复，不能回滚旧二进制。

## 14. 2026-10 钱包增强（迁移 0069–0074）

本节记录在影子验收前补齐的正确性与运营能力。所有迁移只追加列、表、触发器和回填，不重建已有表；新增语义用"现有状态 + 原因列"表达。

### 14.1 充值状态机（0069）

- 停止付款与发起取消不再清空 `checkout_url`。站内是否展示付款入口由 `buyer_abandoned_at`、新列 `cancel_requested_at` 与未结核对单决定；"pending 且无收银台链接（或直付地址）"重新只表示建单结果不明。迁移把此前因此误写成 `create_unknown` 的已绑定订单改回 `pending`，取消和 30 分钟自动关闭对已停止订单恢复有效。
- 首次建单请求体冻结在 `create_request_body`，重试与幂等重放逐字节相同，不受 `tunnel_domain` 变化影响；新请求附带不含邮箱的 `metadata`。
- DujiaoPay 错误按官方 `error.code` 分类（`DUJIAOPAY_*` 码，含 `request_id`）。限流与无容量退避重试；`auth.request_unauthorized` 让渠道立即 `off`、开 case 并告警；同一冻结请求两次被校验拒绝且订单列表在建单窗口内查无此商户单号时，订单以 `cancelled` + `local_close_reason = never_created` 结案并释放待付额度；幂等冲突时按商户单号在订单列表中找回并绑定。
- 已停止订单或已关闭渠道上的未知建单，若本次重放才首次绑定网关订单且其仍为 `pending`，立即执行一次网关取消，不留下买家从未见过的可付订单。
- Webhook 改为验签、落库、绑定、排队后立即返回 2xx，查单由对账循环异步完成（`Notify` 唤醒）。认证查单完成后回写此前 `pending` 的事件为 `processed_by = reconcile`，不再永久阻断恢复和付款。未知订单与测试事件一律 200；DujiaoPay 回调限流放宽到每 IP 每分钟 600 次。
- `new_topups_paused` 独立暂停新充值，影子模式也可用。

### 14.2 入账二次校验与站内直付（0069、0070）

- 订单保存建单、`order.method_selected` 和查单返回的 `gateway_chain/gateway_token_id/pay_address/payable_amount/fx_rate/gateway_expires_at`。
- 入账前除既有身份与回执校验外还要求：`paid_source = chain`；`token_id` 属于该订单冻结的允许方式（直付订单为固定 token）且与链一致；确认数不低于官方各链最低确认数（`src/market_payments/chains.rs`）；`settled_amount` 不少于锁定的 `payable_amount`（仅 USDT/USDC/USDT0 等美元稳定币上，恰等于法币面额时视为网关以法币口径报告；TRX/ETH/BNB 不适用）。不在内置链表中的 `token_id` 无法校验链与确认数，一律进入 `paid_method_not_allowed` 核对。失败分别进入 `paid_method_not_allowed`、`paid_confirmations_low`、`paid_amount_short`、`paid_source_manual` 核对单。`settled_amount` 的确切口径须以真实商户 fixture 锁定。
- 渠道 `order_mode = direct` 时买家选择 token，建单固定链与币；`GET /v1/market-wallet/topups/:id/payment-instructions` 每单每 5 秒最多一次认证查单，只在可付时返回地址与精确金额，站内展示二维码、倒计时与确认进度。

### 14.3 渠道试运行、设置与主密钥（0070）

- `rollout_state`（off/canary/live）见 §5.1；`enabled` 由触发器保持为兼容投影。readiness 的 `channel_no_current_live_topup` 改为 `channel_none_live`。
- `market_payment_channel_settings` 保存托管/直付模式、允许方式、单渠道金额上下限和手续费模型；修改不产生新凭据 revision、不重新试运行。允许方式以渠道设置为唯一来源：整体替换产生的新 revision 复制当前设置，请求里的 `allowedMethods` 只在新建渠道时作为初值。手续费只用于 Owner 总览的成本估算。整体替换不再允许把签名渠道降为仅查单。
- 主密钥支持版本环 `CC_SWITCH_ROUTER_MARKET_PAYMENT_MASTER_KEYS="2:<key>,1:<key>"`；`POST /v1/admin/market-payment-channels/rewrap` 用最新版本重新加密所有 revision。库中已有支付凭据而主密钥缺失时进程拒绝启动，不再静默生成新密钥；启动自检把无法解密的渠道置 `off` 并告警。
- 每日（近 7 天）与每周（全量）以 `GET /v1/orders?status=paid` 扫描各商户，已付未入账的本地单立即排队查单，Router 形状却无本地单的已付订单开 `gateway_orphan_paid_order` 并告警（`market_gateway_sweeps` 可断点续扫）。若已付网关单对应的本地单已按 `never_created` 结案，扫描绑定网关单号、清除结案原因，按迟到付款正常入账，并开 `topup_never_created_contradicted` 告警。扫描在独立任务中运行，不阻塞充值对账与 Webhook 唤醒。订单列表缺少 `total` 或含无法解析的条目时，不能作为"查无此单"的证明。

### 14.4 通知与告警（0071）

- 买家/Provider 通知写入 `market_notification_outbox`，与资金变动同事务；投递渠道为邮件与已绑定的 Telegram（Bark 未接入，见 §14.8），同时作为站内通知列表。安全与服务状态类不可关闭，其余可按类型关闭。
- Owner 告警复用 `operator_alert_signal_outbox`，覆盖严重对账、审计不一致、密钥无法解密、渠道认证失败、连续 5 次查单失败、待核对超 24 小时、身份冲突、孤儿已付单、外部退款、渠道转正，以及新提现/退款/争议。

### 14.5 收入冻结与分域冻结（0072）

- `market_provider_earning_holds` 记录每个冻结的原因（dispute、cleanup_uncertain、service_missing、manual、legacy_unknown）；`disputed` 成为"存在未释放冻结"的派生投影。冻结可叠加，只有全部原因释放后收入才可提现。清理不确定、服务缺失的 case 结案会释放其冻结；迁移把原因不明的历史冻结记为 `legacy_unknown` 并按 Provider 开 `earning_hold_legacy`，由 Owner 显式释放。
- 严重 case 只冻结其范围：`journal_unsealed` 全局；钱包投影/入账证据冻结该用户；Provider 负债冻结该 Provider；期间未履约冻结该合同；外部付款证据冻结全部提现与退款。受冻结的合同被暂停服务而不是继续免费运行，解除后自动恢复。

### 14.6 Owner 资金操作与角色（0073）

- Owner 定义为 `CC_SWITCH_ROUTER_OWNER_EMAIL`（未配置时为隧道域名默认管理员）。财务模式、暂停、渠道凭据与试运行、渠道设置、主密钥重加密、手动认领入账、外部退款冲正、收入冻结的放置与释放、严重 case 结案、提现与退款的标记已付只允许 Owner；其他管理员可查看、审批、处置非严重 case 和 50 美元以内的争议退款。
- `manual-credit`：网关报告已付但来源为商户认领/人工时，Owner 登记转账哈希后入账；回执进入同一唯一索引，journal 动作为 `credit_manual`，不计入渠道转正或切换验收证据。
- `reverse`：商户在 DujiaoPay 登记退款后，按金额从买家可用余额冲正，不足部分记 `owner_loss`。两者都先 dry-run 预览；手动入账每单至多一次，外部冲正允许凭不同外部证据分多次执行，累计不超过原实付；冲正提交必须带回预览的 `expectedShortfallMinor`，余额在预览后变化则返回 409，且只作用于未结的 `external_refund_recorded` case。

### 14.7 提现、退款与合同生命周期（0074）

- 标记已付必须由 Owner 手填转账时间、实际到账额与可选网络费，与申请额不一致须填差异原因；审批人与打款人相同会写入审计。单笔提现上限 5,000 美元，同时最多 3 笔未结。Provider/买家可撤回尚未审批的提现/退款。
- 修改提现地址需邮件一次性验证码（15 分钟、5 次尝试），完成后通知；24 小时冷静期保留。
- 普通余额退款申请已退役；历史外部退款义务保留审计处置。新钱包转账仅允许使用“可用余额 − 已到期未预留服务义务”，详见 §15。
- 暂停合同在第 5 天提醒、默认第 7 天（`CC_SWITCH_ROUTER_MARKET_SUSPENDED_TERMINATE_DAYS`）进入清理终止；因分域冻结暂停的（`suspension_cause = finance_hold`）不计时，冻结解除后从解除时刻重新计时；迁移时已暂停的合同从迁移时刻开始计时，保证都能收到提醒。暂停中的合同可以关闭自动续费。每小时提醒 72/24 小时内余额不足的自动续费和不足一天的按秒预算。
- 收入解锁改为单事务逐笔 savepoint，单批 200 笔。解锁失败的批次加 `manual` 冻结并开 `earning_unlock_failed` case、告警 Owner，不再停在队首阻塞其余收入；case 结案或手动释放后重新参与解锁。

## 15. 消费余额政策、充值维护费与邮箱转账（0075）

### 15.1 账户导航与职责

账户按“安全（API Key／通知）→ 用量 → 资金 → 市场交易”组织：

- 资金：平台余额 `/account/wallet/`（充值、转账、C2C、固定高度滚动的充值记录／钱包流水）。
- 市场交易：Share 交易、Client 交易、Provider 设置 `/account/provider-settings/`。供应商收入整合在 Provider 设置的 `#income` 区域，其后为真实业务联系资料和服务准入／申请收件箱；不再配置对买家的授信或预存。
- 收入不新增独立导航。无财务记录显示空状态；暂停或退役 Provider 仍可查询自己的历史收入。成熟净收益由后台自动计入平台余额，身份冲突和用户封禁会阻止相关资金写入。
- 独立收入旧页及其旧链接分支已删除，不做兼容。其余 `payments/market-readiness/market-access` 页面仍重定向 Provider 设置，`billing` 统一到钱包。disabled／shadow 不能复活旧直付或授信界面。
- Owner 的 DujiaoPay 商户配置仍在 Settings；外部提现及提现地址已退役，供需沟通的联系方式与 C2C 描述各有用途，不等于平台出款账户。

### 15.2 报价与维护费

1. 用户输入实际到账的 USD 余额，默认本金范围为 1–1,000 美元，维护费另加、不占用此范围。Owner 如设置渠道上下限，同样约束到账本金，并与全局本金范围取交集；`GET /v1/market-wallet/channels` 返回权威的 `minCreditMinor/maxCreditMinor`、动态费率、政策版本及渠道版本，输入提示、快捷金额与校验全部使用此本金范围。无有效交集时两端为 null，页面禁止报价／支付并提示切换渠道。调用 `POST /v1/market-wallet/topup-quotes` 不向网关建单，不占待付款名额，报价 5 分钟有效。
2. 使用 Owner 当前配置的费率和 `i128` 中间整数计算：`fee_minor = (credit_minor * fee_bps + 5000) / 10000`，半入到美分；`pay_minor = credit_minor + fee_minor`。费率不是固定 5%，调整费率不缩小或扩大本金范围。例如充值 $1,000，费率为 5% 时维护费 $50、实付 $1,050；费率为 7.25% 时维护费 $72.50、实付 $1,072.50。设置页的渠道上下限明确为“到账余额（不含维护费）”；保留的 `minTopupMinor/maxTopupMinor` 字段也使用本金语义，不能再用它们限制含维护费的实付总额。
3. 页面在支付按钮之前展示到账余额、费率与维护费、实付总额；按钮直接展示实付。提示消费余额不支持提现退款，维护费只在充值收取，转账及消费不再收费。CNY 是实时汇率下的近似展示，USD 为账本权威金额。
4. 建单必须提交本用户的 `quoteId`。订单冻结本金、费率、费用、实付、政策版本、渠道凭据 revision、渠道设置版本和网关成本估算。过期／政策或渠道变更的新建单返回 `MARKET_TOPUP_QUOTE_CHANGED`，展示更新后的总额并由用户再次确认。页面可见时有界刷新渠道范围，切回页面／报价不匹配／服务端拒绝超限时重新获取；配置版本变化立即废弃旧报价，不自动修改输入或按新价格提交。范围错误返回本金限制、当前费率和政策版本，不创建订单／占用待付款名额。
5. 相同幂等键或同一报价重试始终定位原订单；已存在订单以原金额／原请求体恢复，不根据今天的费率重新建单。不同标签页只有财务指纹一致的可付单才能复用。
6. 网关支付金额及现有 `amount_minor` 字段是实付；`credit_amount_minor` 才是余额本金。自动或人工验真入账均将本金计入钱包、费用计入 `platform_fee_revenue`，收到钱之前不能提前确认维护费收入。未付款取消、30 分钟核实、安全继续支付与新标签页跳转保持有效。
7. Owner 在“设置 → 市场 → 平台钱包 → 余额与转账”设置费率和转账限额，使用版本 CAS；修改写不可变审计并发出 Owner 信号。非 Owner 管理员只能读。网关成本使用建单时快照，不能用今天的费率重算历史成本。

### 15.3 邮箱转账

- 仅限本 Router、有效且真实完成邮箱登录验证的用户，精确匹配规范化邮箱；不猜测相似邮箱、不代注册、不暂存未知收款人资金、不能转自己。
- `users.email_verified_at` 表示正常邮箱登录已经证明归属；有效真实登录会话可按迁移 81 修复旧标记，不要求为资金操作再次登录。自动创建用户或 API Key 不能替代登录证明。
- 默认单笔／UTC 自然日各 5,000 美元，Owner 可配置，暂停开关独立。转账不收费，不制造 Provider 收入，不绕过履约与七天沉淀。
- 可转额 = 可用余额扣除已到期、尚未预留的服务义务，再受单笔／日上限约束。钱包 hold 已从可用额中剔除，不重复扣减，也不一次冻结所有未来续费。
- 报价冻结收发用户 ID、双方邮箱及精确 `amount_units`，15 分钟有效。“转出全部”冻结当前所有可转单位；之后新充值不自动追加到已确认转账。
- 显示收款邮箱与金额后直接确认，无二次邮箱验证码。以正常登录会话授权，绑定原报价、收款人和精确金额。邮件服务不可用不阻止转账。
- 每小时最多 30 次收款人报价尝试，失败查询也持久计数，按用户和来源 IP 限制，避免账户枚举。
- 提交时在一个 IMMEDIATE 事务中复核身份、冻结范围、额度与可用额，原子写入复式 journal、双边钱包、不可变转账记录、会话授权证据和两条强制通知 outbox；任一步失败全部回滚。
- 成功重试先返回原结果，即使原报价已过期或转账后来暂停。邮箱投递与页面刷新不参与资金事务，失败不得重复扣款。用户可在双方流水及通知查看金额和对方邮箱。
- API 只读写 Session 所属转账，不开放站外提现或 Owner 代用户无验证转账。

### 15.4 外部退款／拒付与审计

“不支持余额退款”不会使已收到的外部退款／拒付事实消失。保留 Owner 先核对商户证据、dry-run 再冲正的路径。每次外部退款按原实付中本金／费用比例拆分，使用累计舍入差额，最终全额退款恰好冲回全部原费用；累计外部退款不得超过原实付，同一外部证据不得重复处理。扣除原买家尚可用的本金，不足记 Owner 损失；不能追扣已收转账的其他用户，不能改写原 journal 或生成负余额。

新对账视图同时核实本金＋费用＝实付、封口 journal 的完整 posting 和 receipt。真实渠道准入检查复用正确的本金／费用口径；人工认领仍不计作链上验收。邮箱转账独立核对不可变记录、报价、新会话授权（或旧只读挑战证据）、双边两笔钱包 posting；证据异常冻结发送和接收用户，孤儿转账 journal 全局冻结。Owner 不能只点“结案”绕过仍然失败的不变量。

0075 重建 posting 账户类型约束时保留历史 ID、金额和封口，并重建依赖视图与不可变触发器；升级测试必须验证旧 sealed journal、Owner 操作与外键。该结构升级不是将旧 Provider 余额迁入新钱包。

## 16. Provider 平台服务费（0076）

### 16.1 资金口径与边界

Provider 平台服务费是对**已履约收入总额**的分成，不是对 Provider 利润的估算，也不是提现手续费。默认 10%，Owner 可设置 0–100%，精度 0.01 个百分点；0% 关闭服务费。Share 和 Client Host 使用同一套规则。

- 买家仍按商品原售价扣款。100 美元服务全部履约后，默认拆为 Provider 净收益 90 美元、平台服务费 10 美元。
- 用户充值的维护费是另一项独立政策。例如充值到账 100 美元，按 5% 支付 105 美元；消费 100 美元的服务，再由该收入拆出 90／10。不能把两种费用相加称为“用户消费手续费 15%”，也不能在 Provider 提现 90 美元时再扣一次。
- 充值、余额转账、钱包预留、免费服务和试用不产生 Provider 服务费。未履约资金不提前确认为平台收入。
- 净收益与对应服务费一起沉淀至 `max(buyer_debited_at, fulfilled_at) + 7 天`。相关收入受争议冻结时，两者都不解锁；平台不能比 Provider 更早确认可支配服务费。
- 平台服务费的“已结算”是 Router 账本确认，不代表外部银行／链上资金已自动转移。Provider 仍按既有申请、Owner 审批及线下付款流程提现。

### 16.2 政策版本、通知与计费周期

政策与充值维护费分别版本化，修改其中一项不影响另一项报价。`market_commission_policy_control.version` 用于 Owner CAS；政策及其替换记录只追加，不修改历史。

1. 上调相对于当前生效费率的服务费，固定在保存后 7 天生效；下调或维持当前费率立即生效。再次保存会替换尚未生效的调整，页面明确提示这一点。
2. 保存事务同时写 Owner 审计信号和 Provider 强制通知 outbox。收件人覆盖已绑定 Provider 资料、历史合同和收入记录；通知含新费率、生效时间及收入页链接。
3. 报价冻结 Provider、政策版本和费率；合同冻结所接受报价的条款。第一付费月／第一按秒预算以及试用转付费沿用报价，不因后台生效或延迟开通而换费率。
4. 后续月租在下一期开始时间选取政策；按秒服务在建立新的预算时冻结政策。一个已冻结的月租期或预算不会在中途拆换费率，也不以结算 worker 的执行时间选费率。
5. 补建按秒预算有待处理履约观测时，以最早尚未覆盖的服务时间为锚点。升级前已存在的合同、旧收入和旧周期不追收；升级前已经发生但延迟补账的服务也保持零服务费。未来新周期才适用当时政策。这是防止历史重算，不是旧 Provider 余额迁移。

“7 天生效”表示新周期可开始采用该费率，不保证所有在租合同同一天切换。一个月租周期可能晚于该日到期；Provider 价格预览会显示当前费率和已排期调整，实际收入以不可变条款为准。

### 16.3 整数分账、履约和成熟

账本仍以 USD 计价，1 美分 = 86,400 单位。所有比例乘法使用 `i128`，不使用浮点数，也不把每个履约片段先四舍五入到美分。

同一周期累计履约总额为 `gross` 时：

```text
cumulative_fee = (gross * rate_bps + 5000) / 10000
本片段服务费 = 本次 cumulative_fee - 上次 cumulative_fee
本片段净收益 = 本片段履约总额 - 本片段服务费
```

该方式使同一周期的总费用不受批处理切片数量影响。`market_provider_earning_lots.amount_units` 保持原有**总额**含义，新增固定 `commission_units` 和派生 `net_amount_units`；余额、冻结、可提现和提现申请全部使用净额。100% 服务费可生成零净额 lot，其服务费仍正常沉淀／解锁，不能被“净额为零”筛选遗漏。

履约 journal 先保留原始总额证据，再追加分账 journal，将服务费从 `provider_pending` 转入以 lot 为主体的 `platform_commission_pending`。成熟时同一事务分别转入 `provider_available` 和 `platform_commission_revenue`。不可变 split 记录总额／费用的累计前后值及 journal；重试不会重复分账或解锁。

### 16.4 退款、争议与出款保护

- 未履约退款仍全额退回买家钱包，不产生服务费。
- 已履约服务退款按**原 lot 的实际净收益／服务费比例**冲正，不采用今天的费率。分次退款以累计已退总额计算费用差额，最后一次全额退款精确冲回全部原费用。
- 未成熟的退款分别冲回 Provider 待结算和平台待结算；已成熟的退款分别冲回 Provider 可用净额和平台已结算收入。每笔分配记录对应争议、lot、退款总额、净额和费用。
- 可退款总额受该 lot 尚未提现分配／付出的净额约束，使用整数二分求精确容量。不能因为平台还留有一部分费用，就把已线下付给 Provider 的净额虚构成仍可退；超出容量必须由 Owner 先撤回未付款提现或线下追偿，本期不实现自动垫付／追偿单。
- 部分退款后可以补充处理剩余收入，不要求制造新服务。此前“无需退款”的已裁定片段仍受保护；完全退款且没有新履约，不能反复开启空争议。
- 提现创建、批准和开始线下转账都会重新验证所分配 lot 的服务费证据；只冻结和支付净额，不重复计费。已经开始／完成外部付款的处理仍遵守原出款状态机，不能以财务配置变更重写历史。

## 17. 成熟收益转入消费余额（0077）

### 17.1 产品规则与资金边界

Provider 仍有独立的收益应付账，不能将沉淀中的金额直接显示为可消费余额。新增一条**由本人明确选择**的去向：已完成七天沉淀、未被冻结、未分配提现的净收益，可 1:1 转入同一 `user_id` 的现有 USD 钱包。

- 不自动转入，不在余额不足时自动扣收益，不自动购买或自动转给其他用户。
- 不收转入费，不重复收充值维护费或 Provider 平台服务费；原收入的总额／服务费／净额条款不变。
- 转入后可在 Share Market、Client Market 消费，或使用既有邮箱验证转账流程。转入不可撤回，不可再次提现，也不能转回收益。
- 无需提现地址，不调用 DujiaoPay，不依赖某个充值渠道；但要求已验证且有效的用户、已认领且无冲突的 Provider 身份，以及已批准开放的平台钱包财务模式。停止挂售或退休的 Provider 不因此丧失自己的成熟收益。
- 普通消费余额**不提供现金退款**。未履约或服务争议结算调整只能退回买家钱包；外部支付撤销仍须保留原始收据及冲正。它们不是用户余额兑现服务。

### 17.2 账务、并发与已处置保护

每次确认在一个 `IMMEDIATE` 事务中按 `unlock_at, lot_id` 顺序分配精确整数单位，写入：

```text
借：本人 provider_available
贷：本人 wallet_available
```

同事务更新钱包投影／版本、lot 的 `converted_units`、不可变转入记录与分配、封口 journal、审计事件及强制通知 outbox。任何失败整体回滚；不产生新的平台收入或 Owner 真实入金／出款。

`paid_units` 只表示 Owner 已线下实际付出；`converted_units` 只表示内部转入，不混写。可提现／可转入均减去 `converted_units`。数据库触发器禁止减少累计转入，并要求 `held_units + paid_units <= unlocked_units - converted_units`，提现与转入竞争同一余额时最多一方成功。

服务争议不撤回已转入的钱包金额，不挪用其他 lot 的钱弥补。可结算退回容量排除已提现、提现冻结和已转入的净额，并沿用原服务费比例；超出容量转人工核对，本期不新增自动垫付或追偿。

### 17.3 接口、预览及重试恢复

| 接口 | 合同 |
| --- | --- |
| `POST /v1/market-provider-finance/wallet-conversion-quotes` | 只接受 `{all:true}`、整数美分 `{amountMinor:...}` 或明确选择的 `{batch:true}` 三选一；每小时每用户最多 30 次；预览有效 5 分钟，不占用资金。 |
| `POST /v1/market-provider-finance/wallet-conversions` | 必须提交 `Idempotency-Key`、`quoteId`、`termsVersion:1` 和 `acknowledgeNonWithdrawable:true`；重新检查成熟时间、净额、冻结、对账证据与钱包上限。 |
| `GET /v1/market-provider-finance/wallet-conversions` | 本人游标分页；可用 `quoteId` 查询丢失响应的原操作。 |
| `GET /v1/market-provider-finance/wallet-conversions/:id` | 本人单笔详情。 |

以上均要求 Session，并设置 `private, no-store`。金额以字符串整数记账单位返回。自定义至少 1 美分；“全部”保留不足一美分的每个单位，但冻结的是预览时的金额，不会把之后新增收益一起转走。最多分配 10,000 个 lot；超限时提供明确的“核对下一批”，只预览前 10,000 个 lot 的准确金额（允许不足一美分），仍需本人核对和确认。不能静默截断“全部”，也不能让大量极小收益因自定义最低一美分而永久无法转入。

已成功的同键／同预览请求，在预览到期、政策暂停后仍返回原结果。相同键换请求返回冲突，同一预览换键不能重复转入。

浏览器在确认 POST 前按用户保存原预览和幂等键；存储不可用则阻止提交。网络中断、网关 408／5xx 或会话失败保留原操作；刷新页面不会自动 POST，可先查询结果，再由用户明确重试同一笔。只有服务端明确业务拒绝才允许重新核对金额。成功结果须匹配原预览、金额和条款；不能因刷新余额失败就将已成功转入展示为失败。

### 17.5 升级、审计与故障处置

迁移 `0077_market_earning_wallet_conversion.sql` 只增加三个表、lot 处置列、政策暂停列与审计游标，以及索引／约束／证据视图。空库共 224 张表；从 0076 的 221 张表原地升级不重写钱包余额、既有 journal 或已承诺分账。旧迁移及校验和保持不变。

`market_verified_earning_conversion_evidence` 独立验证本人预览、金额／条款／期限、journal 指纹、两个准确 posting 及封口、分配总额、来源 lot 身份／成熟时间和转入序列连续性。逐 lot 累计投影还须与分配之和一致。转入／提现同一事务内复用已核验 parent 证据，避免一个跨多 lot 转入被重复全量核验。

后台持久游标每批轮转核验 200 个 lot 和 200 条转入，并查找孤儿 journal：

- `earning_conversion_missing_evidence`：冻结记录本人、被引用来源 lot 所有人及相关合同。
- `earning_conversion_allocation_mismatch`：冻结对应 lot 的 Provider／用户与合同。
- `earning_conversion_orphan_journal`：全局财务冻结。

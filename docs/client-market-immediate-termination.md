# Client Market 立即退租与补偿

本次改造只适用于 Client Market。Share Market 的到期退出、计量和结算规则不变，也没有增加 Share 退租补偿。余额退回均为平台内信用的返还，不新增外部退款、提现或二次邮箱验证码。

## 用户操作

- **关闭自动续租**：当前已付费周期继续服务，到期退出，不收提前退租补偿。
- **立即退租**：确认后停止访问和计费，异步清理 Client。已关闭自动续租的用户仍可选择立即退租。
- 用户先备份数据；清理会删除 Client 数据和配置。Host 清理失败时停止计费、隔离 Host，继续自动/人工清理；不能把“结束失败租用”当作清理凭证或资金返还凭证。
- 确认清理后，未使用租金按约定返还平台余额。财务异常不会回滚已验证的物理清理，也不会占住可复用的 Host，但异常资金必须完成核对后才能流转。

各处 Client 退租入口共用同一预览与确认组件。钱包页面可查看结算、计费截止时间、清理状态、补偿金额及异议进度。Provider 在原有 Provider 设置的收入区域查看收益和退租记录，不新增独立侧边栏项目。

### Client Market 行内处理工作台

- 原 Host 对应行的操作区显示待答复、待裁决、清理失败等入口、待办数量及答复截止时间；没有待办时保留退租详情入口。不把退租处理混入当前租户的控制菜单。
- Provider 直接在共享弹窗中全部／部分减免或正式答复；Router 财务 Owner 在需要裁决时通过同一弹窗处理。兼有多种身份时可切换处理身份。普通管理员没有财务裁决权限。
- 弹窗按不可变的 `terminationId` 加载原租户、原 Provider、资金状态和分页处理历史。Host 再次出租、转给另一 Provider、下架或删除，不会改写旧退租身份，也不授权新租户／新 Provider 查看旧争议。
- 页面顶部“退租待办”独立分页，不受公开 Host 列表、筛选和分页影响，已删除 Host 的待处理事项仍可找到。普通无争议退租自动清理、结算，不新增 Provider 确认或 Owner 审批步骤。
- 钱包、Provider 设置、财务设置共用同一详情／处理弹窗。站内通知和新增退租邮件中的链接直接定位 `/client-market/?terminationId=...`；新增普通退租及待裁决提醒仅使用去重站内通知，不额外增加邮件。
- 提交后保留弹窗并刷新权威状态；编辑期间不自动刷新覆盖输入，版本冲突须重新核对，不能重复提交旧裁决。加载更多的处理历史和待办不会被轮询重置为第一页。
- 清理重试仅适用于仍绑定原 installation、Host 和 Provider 的失败租用；不能因处理旧争议而清理当前新租户。财务异常只能进入账务核对，不能以责任裁决代替修复，也不能在清理确认前提前返还余额。

## 金额规则

`P` 是当前完整付费日历月实际租金，不含充值维护费。`R` 是截至确认退租时，扣除已交付服务和此前已退回金额后的剩余租金。`r` 是本周期冻结的补偿比例。

主动退出或用户自身问题：

```
C = min(R, round(P × r))
F = R - C
```

`C` 全额归 Provider，不再抽取平台服务费；`F` 退回用户平台余额。补偿不足时不额外扣用户其他余额、不形成欠款，钱包余额为零也能退租。已交付服务仍按原规则收平台服务费。

核实为 Provider/平台原因，或 Provider 同意全部减免：`C = 0, F = R`。正常到期、续费失败、未扣款试用、免费 Client、激活失败不额外制造提前退租补偿。

所有运算使用整数账本单位，1 美元为 8,640,000 units，1 美分为 86,400 units，按单位四舍五入，不能先取整到美分。例如月租 $0.05、比例 10% 的完整补偿是 $0.005。

最终周期必须满足：

```
周期租金 = 已交付租金 + 此前退回 + 本次退回 + 补偿 + 待裁定金额
```

## 规则版本

Client 正式租金扣款成功后已恢复下一次租用的试用资格。退租补偿是否收取、部分／全部减免、争议超时、剩余租金返还平台余额均不取消或再次发放该资格。未付费的纯试用退租继续共用原轮次剩余时间，不能仅凭选择 Provider／平台问题重置。资格不影响当前付费、财务结算或 Host 安全清理，详见 [Client 试用规则](market-client-trials.md)。

Owner 在“设置 → 市场 → 平台钱包 → Client Market 退租规则”中设置比例，默认 10%，范围 0–100%，支持两位小数。

- 新报价冻结规则，购买时继承到合约，付费开始时继承到首个周期。
- 后续周期冻结周期开始时有效的规则；当前周期不会跟随设置变化。
- 升级前没有约定补偿的付费周期不补收；延迟处理的升级前周期也不会因后台补结算获得新费用。
- 策略、报价/合约/周期条款和退租身份、原始金额、计费截止时间不可原地改写。补偿减免只能降低约定上限。

## 责任与争议

用户可以选择主动退租，或提交 Provider/平台问题。**问题说明可留空**，有说明时上限为 2,000 UTF-8 字节。单方选择、客户端故障、网络异常、服务暂停状态都不是 Provider 有责的技术证明。租户可修改 Client 环境，因此健康检查失败本身不能自动判 Provider 有责；但 Provider 未按约定期限正式处理会触发下面的超时免补偿规则。

争议场景清理成功后先返还 `R - C上限`，仅保留补偿大小的金额，不占住整个剩余租金或 Provider 其他合约。Provider 可主动全部或部分减免自己的补偿；部分减免不代表 Provider 有权替用户裁决剩余争议。财务责任由 Router owner 裁定，普通管理员不因此自动取得裁定权限。

已确认补偿在七天沉淀窗口内可提出一次异议，说明同样可选。已受理异议会暂停该笔补偿入账，超过原成熟时间也不会自动给 Provider 入账。退租时已选择 Provider/平台问题并有正数补偿的，确认退租即开始申诉，不必重复发起。

### 72 小时处理期限

- 从持久化的 `dispute_opened_at` 起计 **72 小时**，不是从清理成功或 Provider 首次打开页面开始。双方均可查看截止时间。
- Provider 在期限前可以全部减免、部分减免，或正式提交“不同意减免／请求 Owner 裁定”，正式答复必须有处理说明。聊天、查看记录、刷新页面均不算正式答复，也不改变截止时间。
- 部分减免立即返还已免除部分（须先确认清理）；剩余部分继续冻结，交由 Owner 裁定。正式答复不等于 Provider 有权自行获得争议款。
- **到达截止时间仍未正式处理，自动免除全部尚有争议的补偿，返还用户平台余额。**不是机械返还周期租金的 10%，而是本周期冻结比例、剩余租金上限和已减免情况确定的实际金额。此结果是约定的超时减免，不是平台认定 Provider 技术过错。
- 截止时间到达后，即使后台还没有执行，迟到的 Provider 答复、Owner 维持补偿或用户放弃追讨也不能抢先改变已应生效的超时减免。
- 后台每 30 秒按有界批次、持久游标、逐项 savepoint 处理；停机重启后补处理过期记录。重复执行不重复退回；单笔异常不阻塞其他记录。
- 清理尚未确认时，先记录补偿为零，**不提前释放资金**。确认清理且账务校验通过后再退回完整剩余租金。账务异常按原恢复流程处理，不伪造返还记录。
- Provider 已及时正式答复但仍未解决的争议，不再适用“无人处理”规则；持续冻结该笔争议款，并保留去重的 Owner 待处理提醒。

### 用户主动结束追讨

用户可以在未结束的申诉中选择“结束补偿追讨”。确认弹窗显示实际剩余金额并说明：**该金额归 Provider，不会退回用户；已返还余额不变，申诉永久结束，不能重开。**这是放弃追讨，不是撤销退租或放弃整个剩余租金。尚未清理的仍须确认清理后才结算。

尚未授予的补偿按确认授予时间开始七天沉淀；已授予后申诉的补偿保留原成熟时间，不重新延长沉淀。已部分减免的只结束对剩余部分的追讨，不收回已返还金额。

### 聊天室沟通

退租确认、进度以及钱包/Provider 的退租记录提供原 Client 聊天室入口，在新标签页打开，不打断确认或清理进度。建议双方在此沟通，正式财务处理仍必须使用退租记录中的减免、答复、结束追讨或 Owner 裁定操作。

Client 清理后聊天室保持归档，不恢复安装、隧道或 Host。存在未结束补偿申诉时，仅原买家和 Provider 可继续发言；匿名及其他用户仍只读。申诉结束后恢复归档只读。未结束申诉的聊天室不按普通归档期限删除，结案后保留正常 60 天历史。归档期间的沟通走站内未读，不复活面向在线 Client owner 的邮件投递。

**现有 Client 聊天记录是公开的，不是私密财务工单。**界面明确提示不要发送密码、支付凭证等私密资料；系统不会将申诉说明或财务处理备注自动公开到聊天室。正式申诉、答复和结算邮件使用英文模板、按阶段和收件人去重，轮询或重试不重发。

## 补偿入账

补偿使用独立 award 表，不伪造服务交付片段、不进入普通服务佣金计算。确认补偿后沉淀七天，再由后台自动转入 Provider 的平台余额，可消费、C2C 或转账。

已有已交付收入的成熟时间不变。争议中尚未授予的补偿，在裁定授予时才开始七天沉淀；已授予后提出异议的补偿保持原成熟时间，但必须等异议解决才可入账。减免通过新增反向流水返还信用，不修改已封账分录。

Provider 收入汇总及分页同时包含服务收入和补偿，但明确标注来源。平台资金一览的累计收益入账及冻结收入统计也包含补偿。Host 历史显示服务交付金额和退租补偿，钱包流水分别标注“Client 退租退回”和“Client 退租补偿入账”。

## 事务与恢复

一个安装/合约只能有一条权威退租记录。确认事务使用 IMMEDIATE 锁，将以下内容一起提交：

1. 校验租户、预览令牌、周期及冻结规则；预览有效期 120 秒。
2. 按已有健康/控制证据结清至当前截止时间，包含最后不足一小时的尾段；不因取消未付费试用而启动扣款。
3. 记录原始条款、剩余金额、责任声明、截止时间。
4. 停止续租和后续计费，持久化清理任务，关闭 Client 隧道。

SSH 在事务提交后执行。重复请求沿用原记录、截止时间和任务，不再次扣补偿或退回余额。续租、小时结算与退租共用数据库事务边界。

清理完成路径写入独立、绑定 installation + Host 的凭证，再以 savepoint 执行财务收尾。财务失败保留清理凭证、显示 `finance_pending` 并建立 Owner 核对事项。后台使用持久游标、有界批次和逐项 savepoint 恢复，不会让一笔坏记录阻塞其他用户。

常规清理完成、清理后安装已被清除、Host 重验证、自动 clean probe 都接入同一收尾。历史恢复只认原安装绑定的成功清理任务/凭证，不使用 Host 当前是否空闲来证明旧安装曾被清理；Host 可能已经由新用户租用。没有资金变动的历史免费/试用记录不重放旧邮件。

财务审计包含 Provider pending 负债、周期未履约负债、补偿授予/减免/入账证据和孤立分录。补偿原始授予金额及七天成熟时间不可改写；入账必须绑定本笔补偿的封账分录。普通异步清理不是“人工财务争议”。有真实异常时保留精确负债，不能以“关闭核对事项”替代资金修复。

## 主要接口

- `GET /v1/client-market/termination-policy`
- `GET/PUT /v1/admin/market/client-termination-policy`（修改仅 Owner）
- `POST /v1/client-market/clients/:installation/termination-preview`
- `POST /v1/client-market/clients/:installation/release`（携带 previewId、reason、claim）
- `GET /v1/client-market/clients/:installation/termination`
- `GET /v1/client-market/terminations?provider=false|true&cursor=...`
- `GET /v1/client-market/termination-workspace`（当前身份可见的 Host 摘要、待办总数和服务端时间）
- `GET /v1/client-market/termination-workspace/records?hostId=...&pendingOnly=true&cursor=...`（Provider／Owner 独立工作队列，每页 50 条）
- `GET /v1/client-market/terminations/:id?eventCursor=...`（原买家／原 Provider／财务 Owner 的详情、操作能力与分页时间线）
- `POST /v1/client-market/terminations/:id/dispute`
- `POST /v1/client-market/terminations/:id/waive`
- `POST /v1/client-market/terminations/:id/respond`（Provider 正式答复，expectedVersion、note）
- `POST /v1/client-market/terminations/:id/withdraw`（用户结束追讨，仅 expectedVersion；金额由服务端计算）
- `GET /v1/admin/market/client-terminations?openOnly=true&cursor=...`
- `POST /v1/admin/market/client-terminations/:id/resolve`（仅 Owner）

处理请求使用 expectedVersion；客户端不指定最终扣费或退回金额。Owner/Provider 仅能在冻结的剩余补偿范围内提交 awardUnits 字符串及说明。读取及历史分页受用户身份限制并禁用缓存。

## 运维与验证

数据库使用新增 migration 95，不修改已发布 migration。启动时先备份数据库，按正常升级流程自动建表。上线后检查 Owner 的默认补偿比例，并在新报价中确认条款展示。

行内工作台使用新增 migration 98，仅增加 Host 历史和 Provider 待办查询索引；不改写既有退租、清理凭证或金融记录，不新增资金状态机。

清理失败：按原 Host 清理/重验证流程处理，不直接把 Host 标成空闲。清理已完成但资金待处理：检查 Client 退租记录和财务核对事项，修复具体证据异常，再由后台重试收尾，不重复发起新退租。需要裁定的剩余争议只能由 Owner 处理，不能借用一般服务争议接口结算补偿；Provider 减免、用户结束追讨和无人答复的超时减免均走专门的退租账务路径。

验证包括精确金额与上限、旧周期保护、条款冻结、试用/免费/系统退出、预览过期和越权、重复收尾、清理失败、财务恢复、补偿争议与减免、自动入账、账本守恒和 Share 回归；以及空说明、72 小时边界、可配置比例、未清理超时、成熟后争议返还、正式答复、用户结束追讨、重复/过期版本、自动处理失败回滚与公平重试、归档聊天室权限和保留期限。邮件复用现有英文 HTML 模板，按退租记录、阶段和收件人去重；轮询与自动重试不各发一封邮件。

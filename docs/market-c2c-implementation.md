# C2C 平台余额交易：实现与运维

> 当前资金操作只依赖正常登录，无二次邮箱验证码。迁移 85、86 的授权证据、英文邮件及分渠道降噪／投递规则见 [资金登录授权与通知契约](market-financial-session-notifications.md)。历史迁移的挑战字段仅作只读审计。

状态：已实现，默认关闭。入口沿用“账户 → 平台余额”，管理入口为“设置 → 市场 → 平台钱包 → C2C 设置”。

## 1. 范围与资金边界

C2C 出售的是卖方已有的、可转移的平台余额，不是平台创建新充值款，也不是 Provider 提现。任何正常且邮箱已验证的用户都能成为卖方，不要求 Provider 身份。

卖方开启出售即持续授权自动接单。买方下单时，平台在同一事务中冻结卖方已有余额并启动付款窗口，不再等卖方逐单接单；最终仍需卖方核实收款并以登录会话确认，或由独立处理人裁决才能交付余额。买方点击“我已付款”只是声明，不是平台核实付款。截图、聊天说明、成交次数都不能证明实际到账。

- C2C 不收取平台手续费，不重复计提官方充值维护费或服务佣金；卖方可设置售价。
- 平台余额不提供现金退款。取消订单只会解冻卖方尚未交付的余额。
- Provider 未成熟收益不能参与出售；完成七天沉淀并自动计入平台余额后，才能按相同规则出售。
- Provider 外部提现和手动收益转入已退役，完成沉淀的净收益自动计入平台余额，见 [收益自动到账契约](market-earnings-automatic-credit.md)。官方 DujiaoPay 充值链路不变。
- 用户间转移不会减少平台账面总负债，也不会消除运营方的资金保管、账户安全或争议处理责任。C2C 减少的是逐笔处理线下付款的工作，不是保证零人工介入。

## 2. 默认规则

| 项目 | 规则 |
| --- | --- |
| 平台开关 | 默认关闭，需 Owner 显式开启 |
| 开启出售门槛 | 100 美元可用余额，Owner 可配置；不是保证金 |
| 门槛检查时点 | 首次开启和停止后重新开启；继续出售不要求一直保持 100 美元 |
| 默认单笔范围 | 1–5,000 美元；还受卖方范围、可售余额及钱包转账限额约束 |
| 可配置范围 | 订单最小金额至少 0.01 美元，最大金额不超过 100,000 美元；开启门槛至少 1 美元 |
| 售价 | 面值的 50%–200%，默认 100%；美元或人民币收款 |
| 报价有效期 | 5 分钟，不冻结余额；条款变化后需重新核对 |
| 接单方式 | 新订单自动接单，无逐单确认或接单时限；开启出售时明确授权 |
| 付款时限 | 默认 30 分钟，Owner 可设 5–60 分钟；下单成功时开始，使用报价冻结的时限 |
| 标记付款宽限 | 截止后另留 2 分钟，允许声明已经完成的付款；不是延长付款时间 |
| 首次购入限制 | 首笔成功交付前，每笔不超过 100 美元 |
| 进行中订单 | 买方最多 2 笔，卖方最多 10 笔，同源 IP 最多 6 笔 |
| 创建频率 | 同一用户或 IP 每小时最多成功创建 10 笔订单 |
| 报价频率 | 每用户每小时最多 30 次 |
| 补充说明 | 每用户每小时最多 20 次 |
| 持续出售 | 与页面、浏览器、登录会话及进程重启无关；无需心跳；自动暂停只由真实订单触发 |
| 未付款超时 | 付款截止后加两分钟声明宽限，安全关闭未标记订单、解冻一次；不暂停卖方 |
| 核实提醒 | 标记付款 30 分钟提醒，60 分钟暂停新申请，24 小时通知管理端；绝不自动放行或解冻 |
| 放行授权 | 正常登录会话、亲自核实到账声明、冻结金额与订单版本；不发二次验证码 |

新订单要求 C2C 显式启用、钱包转账已启用且未暂停，并且相关资金范围不存在未解决的严重对账异常。官方充值 `disabled / shadow / enabled` 及市场新购买暂停均不限制 C2C；它转移已有余额，不创建新的网关入金。关闭转账或 C2C 只拦截新报价／新订单及开启出售，不阻止已有订单按证据安全完成或取消。

邮箱登录已证明邮箱归属，开启出售不再要求重复登录验证码。迁移 81 仅从有效、未撤销的真实邮箱登录会话恢复旧账户缺失的验证标记，访问／刷新有效会话也会幂等修复；邮箱字符串、API Token、最近登录时间、过期／撤销会话和停用账户均不能作为修复依据。实际余额转账及订单放行同样只使用正常登录会话和明确操作确认，不另设验证码。

卖方可售金额同时扣除已有冻结、应优先履行的服务资金承诺，并与普通钱包转账共享单笔及每日限额。尚未处理的 C2C 冻结跨午夜继续占用额度；放行当天计入当日已转出。不能通过拆分 C2C 与普通转账绕过每日上限。

## 3. 买卖流程

1. 买方在平台余额中选择“C2C 购入”，选择卖方并填写要获得的平台余额。
2. 查看卖方主动公开的 C2C 描述，核对“到账余额”和“向卖方支付”两个金额，确认线下交易提示。需要沟通收款方式时先联系再下单。报价不冻结资金，不能仅凭描述就提前转账。
3. 确认购入时在同一个 `IMMEDIATE` 事务内校验卖方授权、条款与限额，冻结卖方余额，直接创建 `awaiting_payment` 订单、付款期限和通知。订单固定当时报价中的描述和付款时限，后续编辑不改写原订单。创建失败会一并回滚冻结，不使用后台模拟接单。
4. 买方在订单显示付款窗口后按说明付款，再点击“我已付款”。不要付款后取消，也不要为过期订单继续付款。买方可确认未付款后取消；卖方暂停只阻止新单，不允许单方面取消已经可付款的订单。
5. 卖方亲自检查自己的收款账户，勾选核实声明，直接确认放行。
6. 平台在同一事务内将冻结余额直接交付到买方钱包。没有“先解冻、再普通转账”的竞争窗口。双方总余额不增加。
7. 用户可从 C2C 订单、通知或钱包流水回到订单详情。

界面只有必要操作使用确认，错误在弹窗或所在面板展示，不使用浏览器 Alert。支持中英文、固定高度滚动历史、键盘焦点及移动端；沿用现有 Router 主题。

C2C 卡片始终显示进行中订单／历史。出售入口打开独立弹窗：默认只展开一行必填公开描述和交易责任确认，币种、售价、最小／最大订单在「交易设置」中折叠，摘要仍可见。新卖家默认 USD、100% 面值、1–100 美元（按 Owner 范围调整），不再填写名称、联系人或独立收款资料。显示标识由系统生成，与邮箱及 Provider 身份无关。

卖方确认包含持续自动接单与冻结余额授权，离线、退出登录仍有效；描述应提供可执行的付款或联系方式。旧卖方升级后不会自动扩大授权，显示「待确认自动接单规则」，明确确认一次才恢复展示。原有自动暂停仍需单独恢复，手动暂停／管理员停用保持原样。继续出售的确认不重查开启门槛，停止后重新开启仍需满足门槛。

暂停出售是卡片上的独立操作，只校验本人身份及卖方版本，不要求先填写描述、勾选交易确认或满足开店门槛；平台暂停新交易、低余额或卖方被停用时仍能停止接单。暂停不取消订单或释放冻结。编辑草稿及提交版本在弹窗打开时固定，后台刷新不覆盖；冲突时用户显式重新加载，重载失败就在弹窗内展示错误。

出售资格由后端统一计算并返回结构化原因：未启用 C2C、转账未启用／暂停、账户异常、缺少邮箱登录证明、资金隔离、卖方停用、余额门槛不足。弹窗显示实际准入余额与门槛，并提供保留草稿的「刷新资格」。查询失败不冒充平台关闭；Owner 可直达钱包设置，普通用户不显示无权访问的管理入口。

## 4. 订单状态与异常

| 状态 | 可执行动作 | 超时行为 |
| --- | --- | --- |
| `awaiting_seller`（仅历史 v2） | 卖方接单或拒绝；买方确认未付款后撤回；异常提前付款另行报告 | 按原接单截止安全关闭、解冻一次并暂停卖方新申请 |
| `awaiting_payment` | 新单直接进入；买方声明付款或确认未付款后取消，卖方不能单方取消 | 付款截止立即隐藏付款指引；两分钟宽限后由后台关闭未标记订单并解冻，不暂停卖方 |
| `paid` | 卖方核实到账后直接确认放行；双方可补充说明或发起争议 | 只提醒，不自动放行、取消或解冻 |
| `disputed` | 新自动订单和已接单历史订单可由卖方核实收款后放行；独立授权管理者可依据证据裁决；历史 v2 从未接单的异常付款只允许独立裁决 | 不自动解冻 |
| `released` | 查看交付与审计记录 | 终态，重放不会重复交付 |
| `cancelled` / `expired` | 查看记录；买方可报告延迟付款 | 不重新冻结，不补造余额 |

Owner 只可裁决自己没有参与的争议订单，也可显式授权另一位已登录过的现任管理员为“独立 C2C 争议处理人”。该授权仅增加 C2C 裁决能力，不增加其他钱包权限；撤销授权、失去管理员身份或账户停用后即不可裁决。任何当事人包括 Owner 都不能裁决自己的订单。裁决须提交证据参考、确认已核实双方陈述并匹配订单版本，只交付已有冻结余额或归还卖方，不从平台资金垫款。未配置独立处理人时，买方页面提示 Owner 交易的争议处理限制。

仅历史 v2 未接单前已经线下付款的买方，应使用折叠的“报告异常付款”，不能按未付款撤单。申请转入争议，保留原冻结；卖方不能直接放行，须由独立处理人核对。后台不以接单超时解冻这种订单。新 v3 订单没有待接单阶段，但仍必须等下单成功并显示可付款后才付款。

已关闭订单的迟到付款另行报告。双方可继续补充证据，Owner 只记录外部处理结果，绝不重开已释放的冻结或自动向买方记入余额。需要重新转移余额时应走正常、明确授权的转账流程，而不是重用原订单。

### 不确定结果与重试

- 浏览器在请求发送前保存用户、原始报价和幂等键；保存失败时禁止提交。
- 响应丢失时先按原报价找回订单，必要时只重试原请求。报价过期、卖方停止接单、平台暂停后仍能找回已创建的订单。
- 恢复出的订单必须匹配原始买方、卖方、报价、到账金额、收款币种、汇率、售价、卖方标识及描述快照。
- 恢复数据损坏时先查询该用户的进行中买单，不允许静默生成新的幂等键。已有订单先处理；确认无进行中买单且存储可用后才恢复新下单。
- 普通错误、限流、登录失效、未知冲突和 HTTP 超时都不能作为“肯定没下单”的证据。
- 更新、放行、裁决采用订单版本检查。新说明或争议改变订单版本后，必须重新查看当前订单并确认到账，不得以旧版本放行。

## 5. 记账、对账与恢复

数据库迁移 `0078_market_c2c.sql` 新增策略、卖方、报价、订单、不可变事件、邮箱挑战和频率记录七张表。不会改写已有钱包余额和流水。

迁移 `0080_market_c2c_description.sql` 增加公开描述，删除卖方档案中的旧联系方式／收款方式／私密收款字段。已有卖家统一暂停并增加版本，须自己填写公开描述并重新发布；不会将原私密资料拼接后公开。历史报价中的私密字段仍是不可变交易证据，仅在获准访问的旧订单详情返回 `legacyPayment`，不用于新报价，也不进入列表；旧订单及冻结正常履行。迁移不改动任何钱包余额、冻结、订单状态或历史报价条款，不新增表。

迁移 `0083_market_c2c_acceptance.sql` 曾引入 v2 逐单接单并移除卖方心跳，新增独立处理人授权表。已有启用、手动暂停、管理停用状态保持原样；旧 v1 订单及其付款期限和财务证据不变。历史 v2 订单仍按原规则完成，不能删除保护已有交易所需的代码。

迁移 `0084_market_c2c_auto_accept.sql` 将新报价／订单切换为 v3，并移除当前策略的接单时限。卖方原开启意愿及暂停状态不变，新增授权版本／时间，只有显式确认 v3 规则后才允许新报价和新订单。不可变报价冻结授权时间和付款时限；订单直接进入待付款，不伪造 `accepted_at` 或卖家接单事件。新订单的付款期限由数据库约束绑定到创建时间及报价分钟数，不能重试延期。旧 v1/v2 提交只可恢复原订单，未使用的旧报价不能新建订单。报价、订单、事件和挑战在同一事务内重建并保留所有原字段，外键始终开启，余额与账本不改写。过期的 v2 升级通知和已经确认完成的授权提醒在投递前丢弃。

| 动作 | 钱包效果 | 必需证据 |
| --- | --- | --- |
| 下单 | 卖方可用减少、冻结增加，总额不变 | 精确匹配的两项分录及账本封存；冻结与订单一一对应 |
| 未付款关闭 | 卖方冻结减少、可用恢复，总额不变 | 原冻结证据和精确解冻分录 |
| 放行 | 卖方冻结及总额减少、买方可用及总额等额增加 | 不可变报价、原冻结、独立放行分录、订单交付标记 |

金额按整数最小单位记账，1 美分对应 86,400 个内部单位。线下应付额使用整数计算，人民币报价使用现有实时汇率缓存及其新鲜度校验；汇率、售价、卖方标识和公开描述在报价中冻结，后续修改不重写订单。

倒计时通过 `X-Router-Server-Time` 响应头授时，后续使用浏览器单调时钟推进，不依赖用户电脑的日期设置；服务端始终独立校验实际付款截止时间。

验证视图校验美元资产、钱包所有人、资金来源、指纹、分录数量与准确金额。全市场对账每次轮转检查 200 笔 C2C 订单，并有界检查孤立账本；不会永远只检查前 200 笔。

- `c2c_evidence_mismatch`：阻止相关买卖双方移动有风险资金，证据恢复前不能直接忽略。
- `c2c_orphan_journal`：全局资金安全拦截，不能通过关闭普通工单绕过。
- 即便证据异常，买方仍可在规定时限内记录付款声明，防止真实付款被未付款超时任务关闭。
- 超时任务每轮最多处理 100 笔未付款订单及 100 笔提醒，跳过已知证据或钱包投影异常，避免一笔坏数据饿死其他超时处理。
- C2C 后台处理使用独立的 30 秒定时任务及独立事务，不会被网关充值查单的网络等待拖延。关闭未付款订单会有最多一轮正常调度间隔，不能将界面倒计时当作已完成解冻的证明。重启后由持久化订单继续处理，不依赖浏览器存活。
- 关闭 C2C 或暂停新交易不妨碍履行原有订单。严重对账拦截仍优先于余额交付。

## 6. 权限、隐私及通知

用户接口均要求登录，并返回 `private, no-store`。订单详情和事件只允许买卖双方查看，管理员检查入口沿用现有管理员权限，策略修改、卖方停用及争议裁决仅限财务 Owner。

卖方列表向登录用户展示系统生成的稳定标识、主动发布的描述、币种、售价、额度和实际完成数。描述最多 300 个字符，服务端合并换行及多余空白为单行；界面明确说明它是公开内容。描述可包含联系方式、支付方式或链接，但不渲染 HTML、不嵌入媒体、不请求链接预览；只将显式 HTTP(S) 链接作为新标签页外链，使用 `noopener noreferrer nofollow ugc`，带账号密码的 URL 不生成链接。报价确认和历史证据按纯文本显示；付款窗口结束后不显示可继续付款的指引。

系统不会将描述、历史收款账号或证据备注自动复制到通知邮件；双方自行提交的证据说明仅在订单权限范围内可见。邮件仅使用英文白名单模板，提供登录后的详情入口，不直接执行放行。

成交数是记录，不是可信度排名，页面按售价和稳定 ID 排序，不将可刷成交量升级为平台认证。Owner 可依据投诉暂停卖方新接单，但不能借此抹去已有义务。

用户在站内查看所有订单事件。买家标记付款仅向卖家发邮件；普通创建、备注、未付款关闭不发邮件，成交双方各收到一份角色明确的回执。争议或延迟付款产生 Owner 待处理信号；裁决或卖方完成争议放行后发出已解决信号。卖家放行的不可变会话授权与订单、金额和版本绑定，邮件投递不授权或阻止资金交付。

## 7. API 索引

用户前缀 `/v1/market-wallet/c2c`：

- `GET /policy`，`GET|PUT /seller`，`POST /seller/pause|resume`（仅 `expectedVersion`）。旧 `/seller/heartbeat` 返回 `410`，不再续期。
- `GET /sellers`，`POST /quotes`，`GET|POST /orders`。
- `GET /orders/:id`，`GET /orders/:id/events`。
- `POST /orders/:id/paid|cancel|dispute|late-payment|notes`；`accept|reject` 仅用于尚未完成的历史 v2 申请。
- `POST /orders/:id/release`（`expectedVersion`、`acknowledgeReceived`）。

管理员前缀 `/v1/admin/market-finance/c2c`：

- `GET|PUT /policy`，`GET /sellers`，`POST /sellers/:id/suspension`。
- `GET /orders`，`GET /orders/:id`，`GET /orders/:id/events`。
- `POST /orders/:id/resolve`。
- `GET|PUT /dispute-handlers`：Owner 专属、版本化授权或撤销，不接受给自己授权。

历史、卖方和事件采用游标分页，管理员与普通用户都能继续查看第一页之后的数据。新建订单要求 `Idempotency-Key`；一个报价最多产生一个订单。

## 9. 整体 review 结论

本轮重点复查了余额守恒、并发冻结、跨午夜共享限额、终态重放、订单权限、不可变会话授权证据及管理员利益冲突。已补齐的边界包括：

- C2C 金额使用独立解析器，避免被官方充值的 1–1,000 美元限制误伤 Owner 默认 5,000 美元设置。
- 下单结果不确定或恢复存储损坏时先核对原订单，不能静默重复下单；变更响应不能切换订单或改写财务条款。
- 倒计时使用服务端授时，快慢 24 小时的电脑均不能重新显示已截止的付款指引。
- 付款声明在证据异常期间仍可记录；严重证据异常阻止余额交付，不能通过忽略工单绕过。
- 冻结、归还及买卖双方交付流水都能回到原订单；卖方主动完成争议放行会同步解决 Owner 提醒。
- 通知不复制收款账号、联系方式、证据说明或验证码；争议状态保留警示底色，文字采用现有高对比度颜色。
- 超时清理独立于网关查单执行，避免官方充值网络异常占用 C2C 订单容量和延迟解冻。

首轮 C2C 上线实现已通过全市场回归 434 项、数据库迁移 48 项、C2C 专项 27 项、通知专项 8 项及前端 38 项单测（此处为首轮记录，不代表后续版本测试数量）。本地构建环境无法访问 Google Fonts 时，可使用离线字体夹具与 webpack 进行代码验证；该测试构建不能作为部署产物。仓库整体格式检查存在其他既有文件的格式差异，不批量改写无关文件。

实现不等于生产验收：尚未部署、未进行真实邮件投递与线下支付。启用前需按第 8 节完成受控验收。线下是否实际到账、支付撤回或双方证据冲突仍不能由 Router 自动判定；争议需要运营方人工处理。

# 资金操作登录授权与通知契约

本契约对应迁移 85、86。取代早期文档中的资金验证码流程，不改变正常邮箱登录；不恢复现金退款、提现或人工收益转入。

## 1. 交互与安全边界

- 邮箱转账：填写收款人和金额 → 查看冻结报价 → 确认转账。无发送、输入、重发交易验证码。
- C2C 放行：卖家打开订单 → 亲自检查自己的收款账户 → 勾选到账声明 → 确认放行。买家的付款声明不是到账证据，平台不自动放币。
- 不引入新的 PIN、近期登录、再次邮箱登录或其他替代挑战。正常会话过期时只走原有登录／刷新流程。
- 写请求必须持有真实 Router 登录会话的显式 Bearer；API Key 和仅自动附带的 Cookie 不能授权转账／C2C 写入。浏览器 Origin 必须与 Router 配置的 origin 一致；拒绝跨站请求。无 Origin 的 API 调用仍需有效登录 Bearer。
- 账户正常、双方身份、精确收款人、冻结金额、版本锁、可用额、共享限额、财务隔离、事务和幂等约束全部保留。历史 v2 从未接单的异常付款仍须独立处理，不能借新流程绕过。
- 登录会话泄露即可能危及余额。这是“只依赖登录”的明确边界，不能声称邮件通知能替代授权或阻止盗用。站外链接只进入登录后的详情，不直接执行资金操作。

转账确认请求为 `POST /v1/market-wallet/transfers`，提交 `{quoteId}` 和原幂等键。C2C 放行为 `POST /v1/market-wallet/c2c/orders/:id/release`，提交 `{expectedVersion, acknowledgeReceived: true}`。旧验证码路由已移除；旧 `challengeId/code` 字段不兼容，新请求携带时拒绝处理。

每笔新转账／卖家放行在同一资金事务中保存不可变的会话授权证据：操作人、非密钥会话引用、认证来源、会话认证／到期时间、对手方、业务对象、精确金额、版本、指纹、确认声明和操作时间。不保存原始 access/refresh token，不关联可过期删除的会话行。退出或清理会话不会破坏历史账本证据。

迁移保留旧转账与已封存的 OTP 审计证据，但挑战表只读，不能再产生、消费或清理金融验证码。原有历史记录与 sealed journal 不改写；新记录只能使用会话授权。

## 2. 通知矩阵

资金事实和全部订单事件仍在原事务中写入站内记录。是否外发按收件人和目的判断：

| 事件 | 邮件 |
| --- | --- |
| 官方充值到账、外部已核实冲正、确需处理的付款核对 | 一份英文回执／通知；到账与核对为必需通知 |
| 普通未付款关闭／取消、自动收益逐批到账 | 仅站内，不发邮件 |
| 普通余额转账 | 发送人与接收人各一份角色明确的回执，不算重复 |
| C2C 创建、普通说明、普通设置、未付款取消／到期 | 仅站内 |
| 买家标记付款 | 只通知卖家，明确“买家声明，不是到账证明” |
| C2C 放行完成 | 买卖双方各一份成交回执，不再叠加普通转账回执 |
| 付款未处理提醒 | 只提醒卖家；同一订单同一提醒目的不随版本重发 |
| C2C 争议、延迟付款、升级处理 | 通知需要行动的另一方和有效独立处理人，不重复通知发起者 |
| 卖家自动安全暂停、管理端停用／解除 | 安全通知；普通编辑保存不发邮件 |
| 余额／续费不足 | 同用户同 UTC 日期合并，发送前重新检查当前资金与服务 |
| 服务恢复 | 同用户五分钟窗口合并；暂停、终止警告和终止仍保留 |
| Provider 服务费改变、收入冻结／解冻、服务争议决定 | 保留重要通知 |

过时的核对单、已付款或关闭后的付款指引、已恢复服务的缺款提醒、失效处理人的指引不再重试发送。只读历史记录仍然可见。通知偏好不再列出已退役退款、普通关闭和自动收益邮件。

服务暂停按同一次持续暂停的起点去重，不使用后台轮询也会更新的时间。
余额不足重试不能离开暂停状态；真实恢复后再次暂停才是新事件。迁移 89
保留历史审计并停止重复积压，详见 [服务暂停通知与历史积压恢复](market-service-suspension-notifications.md)。

## 3. 邮件展示

所有资金邮件的主题、正文、纯文本备选、按钮和页脚仅使用英文。沿用登录验证码邮件的 TokenSwitch 品牌外框，采用“结果 → 金额 → 必要事实 → 一个详情入口”的层级，不引入新站点风格。邮件客户端不可靠支持 CSS 变量，使用现有 inline style 和系统字体。

金额全程整数计算，通常两位小数，必要时最多六位；不展示记账单位。官方充值分开列明到账本金、维护费、实付；C2C 区分 USD 平台余额与实际线下支付币种／金额。时间显示 UTC。

只读取白名单结构化字段，不拼接用户描述、联系方式、证据备注、网关原始状态／错误、支付链接、验证码或密钥。文本 HTML 转义，业务 ID 通过 URL 参数编码。转出回执提供保护账户与联系管理员的安全指引，不再使用“意外收到无需操作”的登录页脚。

站内与 Telegram 可继续使用现有双语文案，均不再提示交易验证码。

## 4. 投递、幂等与失败

`market_notification_outbox` 继续承载业务和站内事件；新增 `market_notification_deliveries` 独立记录每个渠道，唯一范围为收件人、渠道、业务通知目的。邮件成功、Telegram 失败时只重试 Telegram。

网络发送前持久化信封、模板版本和固定幂等键。首次尝试后正文、收件目标、幂等键不可重写；重试复用同一信封。记录服务商 message ID、次数、下次时间和脱敏错误。尊重 Retry-After，单渠道最多八次；超出邮件服务的安全幂等时窗（保守取首次尝试后 23 小时）不盲目重发，标为 uncertain。凭据身份变化、收件人变化也不把旧请求发送到新目标。

Telegram 没有幂等键：在途超时或进程中断后无法确认服务商是否已接受时记录 uncertain，避免声称 exactly-once 或无限重发。明确的可重试拒绝仍可有界重试。

Worker 即将投递时才领取一条事件，避免先领一大批再串行耗尽租约。事件完成使用领取代次 CAS，渠道完成使用独立 claim token CAS；旧 worker 不能覆盖新尝试。外部网络调用不持有数据库锁。

未配置渠道标为 blocked_config，不冒充邮件已发送，不阻止资金事务或后续正常操作；配置好邮件后不批量补发历史通知。历史 sent 事件迁移后不重新外发。站内记录是可靠可查的业务事实，外发邮件不作为付款凭证。

## 5. 回归与部署

执行资金转账、C2C、通知、资金对账及全量 schema 升级／重复启动回归；核对旧挑战证据保留、新会话证据不可变、事务失败回滚、并发不能重复花费、双边回执不重复。

前端执行类型检查、钱包单测及模拟 API 浏览器测试，验证无验证码入口、保留确认与到账声明、超时重试复用原幂等键、账户切换／权限隔离、四种宽度 DOM 几何和键盘操作。不做 UI 截图、不发真实邮件、不执行真实资金操作。测试字体网络不可用时仅通过本地字体夹具完成构建，不改生产字体配置。

邮件、Telegram、DujiaoPay 的真实配置与投递验收属于部署环境联调；本地 fixture 成功不代表外部服务已通过生产验收。
